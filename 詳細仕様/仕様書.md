# BitsKeep 部品在庫管理システム 仕様書

---

## 1. 目的（絶対にブレてはいけない軸）

> **電子回路設計者が「使うべき部品」を最短で判断できるようにすること**

---

## 2. ユーザー種別と権限

| 種別 | 権限 |
|---|---|
| 閲覧者 | 検索・閲覧・データ出力のみ |
| 編集者 | 入出庫・部品編集 |
| 管理者 | マスタ編集・ユーザー管理 |

- ログインIDは当面 `メールアドレス` を維持する。
- 表示名は `users.name` を使い、画面上の呼称やユーザーメニューにはメールアドレスではなく表示名を優先表示する。
- `メールアドレス` はログインIDに加え、パスワード再設定、招待、将来の通知・確認メールの送信先として扱う。
- SNSログインは別レイヤの認証手段として将来追加を検討する。初期候補は `Google` と `GitHub` とし、ローカル認証を廃止せず併存させる。
- SNSログインを導入する場合は、`verified email` を軸に既存ユーザーへ安全に紐付ける。認証プロバイダ情報は `user_auth_providers` のような別テーブルで管理する。

## 4. 機能一覧

### コア機能
- 簡易フリーワード検索（名称・型番・備考）
- フィルタ検索（部品分類・商社・在庫タイプ等、AND条件）

- 類似部品検索（同一機能・近似スペック）
- 既存部品への入庫・出庫処理
- 部品データ編集
- 新部品登録（既存部品情報の流し込み対応・CSVインポート対応）
- 部品情報削除（論理削除）
- 案件部品価格リスト（商社選択可能）
- 棚卸機能
- 使用履歴（日時・出庫者）
- 在庫警告機能（部品ごとの在庫下限設定）
- ユーザー管理
- マスターテーブル編集
- 案件参照管理（Notion事業DB自動発見同期 + 独自案件 CRUD）

### 付加機能
- パッケージ一覧（画像・3Dモデル・PDF管理）
- 受動部品ネットワーク/分圧設計（抵抗/容量ネットワーク・通常分圧・VR分圧・E系列近似算出）
- エンジニア向け電卓（進数混在・単位接頭辞・履歴・定数/関数・数値解法）
- 設計解析ツールハブ（受動部品ネットワーク/分圧設計、ADCコード/スケーリング、誤差/歩留まり、電解コン寿命、NTC/PTC温度変換、シャント、I2C/UART/ロジックレベルを含むIF余裕、電源余裕、バッテリー稼働、ヒステリシス、ロジックIC参照、熱設計、周波数応答、コネクタ設計/ピン配置）
- Altium Designer用ライブラリDB連携（専用テーブルへの追加・更新・削除）
- Notion案件マスタ自動発見・同期（`010_xxx`〜`099_xxx` 事業配下の `01_案件管理`）

## 6. データモデル

### 設計方針

| 管理内容 | 採用パターン |
|---|---|
| 多対多の関係 | 中間テーブル |
| 数値スペック（定格・寸法等） | `component_specs`（spec_typeで区別） |
| 不定型・自由入力項目 | `component_attributes`（キーバリュー） |
| 在庫の物理単位 | `inventory_blocks`（ロット・リール単位） |
| 入出庫履歴 | `transactions` |
| 外部案件ソース統合 | `projects` に `business_code` / `business_name` / `source_type` / `source_key` を持たせて統合管理 |
| 操作監査 | `audit_logs` |

`components` は最小情報（型番・名称程度）で登録可能。段階的入力を前提とする。

### テーブル一覧

| テーブル名 | 用途 |
|---|---|
| `components` | 部品基本情報（型番・通称・在庫数・入手可否・ファイルパス等） |
| `component_series` / `component_series_value_policies` / `component_series_values` | 部品シリーズと値展開ポリシー。抵抗・コンデンサ等の値違い部品を、実部品化前の候補値と実部品に分けて扱う |
| `analysis_sessions` | 設計解析ツールの入力条件、判定結果、コピー用サマリ、候補リンク、案件・部品・BOM行への保存先 |
| `component_specs` | スペック値（定格・寸法・電圧・電流等、単位付き） |
| `spec_groups` / `component_spec_group` / `spec_group_spec_type` / `spec_types` | 部品分類、部品への分類付与、部品分類ごとの候補スペック詳細、スペック詳細。`spec_groups` を UI 上の部品分類に対応する内部データとして扱い、API は `/api/spec-groups` へ統一する。共通スペック詳細は `spec_types.spec_scope='common'` で扱う |
| `spec_templates` / `spec_template_items` | 部品分類ごとの推奨スペック入力テンプレート |
| `component_attributes` | 柔軟な属性追加項目（キーバリュー） |

| `categories` / `component_category` / `category_spec_group` | 旧部品分類と旧推薦リンク。移行で `spec_groups` / `component_spec_group` / `spec_group_spec_type` へ吸収し、通常実装・API一覧では参照しない。`/api/categories` は廃止し、新規実装は `/api/spec-groups` を使う |
| `package_groups` / `packages` / `components.package_id` | パッケージ分類とパッケージ詳細。1部品は1パッケージ詳細を持ち、詳細の並び順はパッケージ分類内で管理する |

| `locations` / `component_location` | 保管棚・QRコード対応の場所管理（階層構造あり） |
| `suppliers` | 商社マスタ |
| `component_suppliers` | 部品ごとの仕入情報（単価・商社型番・URL） |
| `supplier_price_breaks` | 数量条件ごとの単価定義（価格ブレーク） |
| `shipping_rules` | 商社ごとの送料条件（閾値・送料） |
| `inventory_blocks` | 在庫単位（パッケージ種別・ロット番号・リールID等） |
| `stock_orders` | 発注記録（部品・商社・数量・状態・発注日等） |
| `transactions` | 入出庫履歴（誰が・いつ・どれだけ・理由） |
| `component_altium_links` | Altium連携情報（sch/pcbライブラリパス・名称） |
| `users` | ユーザー情報（表示名・役割・認証情報） |
| `audit_logs` | 操作履歴ログ（変更差分をJSON形式で記録） |

### ファイル保存の成功条件

- 画像・データシートの保存成功は、`DBの path 更新` ではなく `実ファイルが保存先に存在すること` を含めて判定する
- 保存先ディレクトリへ書き込めなかった場合は、DB更新をロールバックし、UIへエラー応答を返す
- つまり「ファイルが存在しないのに path だけ登録される状態」は許容しない

### 入力モーダルの閉じ方

- 情報入力を伴うモーダルは、画面外クリックだけで閉じてはならない
- 閉じる操作は `×` `キャンセル` `明示的な閉じるボタン` に限定する
- 未保存変更がある入力モーダルは、閉じる前に確認を出す

### カスタムフィールドの保存条件

- カスタムフィールドは `key/value` の両方が埋まっている行のみ保存対象とする
- `key` の重複は許可しない
- 空行や片側だけ埋まった行で保存しようとした場合は、UI側で保存不可にする

### 発注追跡（stock_orders）の動作仕様

発注リストの送信後も、どの部品・商社の発注がいつ完了したか・キャンセルされたかを追跡できるようにするための機能。

#### データフロー
1. **在庫警告画面で部品選択 → 発注リスト作成**
   - 部品チェックボックスで選択 → 「発注リストに追加」で草稿作成
   - ローカルストレージに `orderDraft` として保持
   - 発注済み部品（stock_orders.status='pending'）は選択不可にする

2. **発注リスト送信**
   - 商社別グループを確認 → 「発注」ボタンで POST /stock-orders
   - 各部品1行ごとに stock_orders レコード作成（`status='pending'`）
   - 送信後、orderDraft をクリア（localStorage 削除）

3. **発注状態の確認**
   - 在庫警告画面で「発注済み」バッジを表示（stock_orders で pending/received の判定）
   - GET /stock-orders/component/{id}/pending で該部品の pending 発注を取得
   - 同じ商社への重複発注を防止

4. **発注受取・キャンセル**
   - 発注商社から納品が来たら、管理者が stock_orders の `status` を `received` に変更
   - 発注をキャンセルする場合は `status` を `cancelled` に変更
   - 状態変更時は `received_date` または `expected_date` を更新

#### UI上の見え方
- **在庫警告一覧**: 既に pending 発注がある部品の行に「⏳ 発注待ち」バッジを付与
  - バッジにマウスオーバーで「商社X: 数量10 (2026-04-20 注文)」などを表示
- **部品詳細**: 「発注状態」セクションで pending/received/cancelled の一覧を表示
- **発注モーダル**: 新規追加前に「この部品は既に商社Xへ20個発注待ちです」と警告

#### API エンドポイント
| エンドポイント | メソッド | 説明 |
|---|---|---|
| `/stock-orders` | GET | 発注一覧（フィルタ対応） |
| `/stock-orders` | POST | 発注作成 |
| `/stock-orders/{id}` | PATCH | 発注状態更新（status/dates） |
| `/stock-orders/{id}` | DELETE | 発注削除（キャンセル扱い） |
| `/stock-orders/component/{component_id}/pending` | GET | 該当部品の pending 発注取得 |

### UI プロトタイプ（リポジトリルート）
`詳細仕様/UI構成/xxx .html` ファイルはインライン CSS を持つスタンドアロンのデザインモック。
Blade+Vue ページを実装する際のビジュアル参照として使用する。

### 全体共通

### 設計解析ツール方針
- 単純な公式を1回解くだけの数値計算器は優先しない。採用対象は、ばらつき・寿命・通信余裕・電源余裕・固定小数点コード化など、実務で判断が面倒なものとする。
- 単機能の公式計算が必要な場合も、それ単体ではなく `最悪値` `3σ` `外れ値率` `温度依存` `在庫/E系列候補` `コード生成` `可視化` のいずれかを伴う形へ昇格させる。
- 探索・候補選定のために既存URLを持つツールも、判断対象が回路設計であれば設計解析ツール群に含める。抵抗/容量ネットワーク探索、分圧、可変抵抗は設計解析ツール内の `ネットワーク探索` / `分圧` / `可変抵抗` メインタブにも同じ操作面を埋め込む。
- 通常分圧とVR分圧の正本は `分圧` メインタブに置く。`NTC/PTC温度変換` は温度-抵抗モデル、温度-電圧グラフ、感度の良い/悪い温度域、測定対象温度範囲の感度、サーミスタ電力損失、自己発熱、抵抗公差/サーミスタ公差の電圧破線、ADCコード、線形化、固定抵抗候補に責務を絞り、電気的な通常分圧/VR分圧候補は共通分圧エンジンを使う。
- 設計解析ツールの数値入力欄は、HTMLの `number` 型で接頭語入力を弾かない。`10k`、`100n`、`10m`、`1T`、`512KiB` のような工学表記を受け付け、入力中に表示表記を保持したまま標準数値へ換算する。入力ラベルの単位は `V` / `A` / `Ω` / `F` / `s` / `W` など接頭語なしの基準単位へ寄せ、初期値・サンプル値は `100k`、`10m`、`100u` のように数値と接頭語だけで表示する。ユーザー入力として `10kΩ`、`100nF`、`10mA` のような単位付き表記も互換受け入れする。SI 接頭語は `Y/Z/E/P/T/G/M/k/無印/m/u/n/p/f`、IEC 接頭語は `Ti/Gi/Mi/Ki` を扱い、IEC を10進接頭語より先に認識する。
- `R1` `R2` `Rs` `Vref` のような回路記号を扱うツールは、入力欄だけで完結させない。簡易回路図またはブロック図を表示し、図中記号、入力欄、計算式、判定結果を対応付ける。
- 画面上の表示順は、全ツールで `仕様・前提確認`、`パラメータ入力`、`結果確認`、`次アクション` を崩さない。最終判定、コピー用サマリ、保存、登録部品取り込み、保存済み解析差分は、各ツール固有の入力面と結果プレビューより後ろに置く。
- 入力ラベルは `R1 (Ω)` のような記号単体ではなく、`R1 上側抵抗` `Rs シャント抵抗` のように役割名を含める。回路上の位置が分からない状態は完成扱いにしない。
- `便利ツール` 配下の既存Excel群は、マクロ実行基盤としてではなく、数式・表・参照データの移植元として扱う。

### 2026-07-30 データシート解析のサーバ側実行（Codex CLI 方式）

**実装状況（2026-07-30 時点）**
- 本ドラフトはユーザー承認済みであり、アプリ側の実装は完了している。
- 未完了は本番サーバ側の前提整備（Codex CLI、poppler-utils、サーバ上ログイン、キューワーカー常駐）と、実データシートでの所要時間・精度・利用枠消費量の実測のみ。手順は README の `サーバ内解析のセットアップ（管理者向け）` に置いた。
- 実装物: `datasheet_analyses` テーブル、`App\Models\DatasheetAnalysis`、`App\Services\Datasheet\*`（解析エンジン差し替え口、Codex 実行、PDF 前処理、結果正規化、分類推薦、スキーマ提供）、`App\Jobs\AnalyzeDatasheetJob`、`App\Http\Controllers\Api\DatasheetAnalysisController`、`resources/js/pages/component-create/serverAnalysis.js`、連携設定の解析方式選択。
- 既存の重複定義は解消済み。解析結果の正規化は `GeminiService` から `DatasheetResultNormalizer` へ、分類候補とテンプレート推薦は `ComponentHelperController` から `DatasheetRecommendationDecorator` へ抽出し、同期解析経路とキュー解析経路が同一処理を通る。

**背景**
- 現行の主導線 `Tampermonkey + ChatGPT Web 自動解析` は、他社 UI の DOM に完了判定を賭ける方式であり、応答完了判定、タブ死活監視、ストール誤検知の不具合対応が恒常的に発生している。
- 解析対象 PDF は `TempDatasheetService` によって既にサーバ上（`storage/app/component-helper-temp/{token}.pdf`、TTL 2時間）へ保存済みである。ChatGPT タブは「その PDF を ChatGPT の画面へ食わせる」ためだけに存在しており、入力経路としては不要な迂回である。
- ブラウザタブに解析が紐づくため、タブを閉じる・リロードすると解析結果が失われる。

**目的**
- データシート解析をサーバ内で完結させ、ブラウザタブへの依存を断つ。
- 既に契約している ChatGPT の利用枠を使い、API 従量課金を増やさずに解析できる状態にする。

**採用方針**
- 解析実行主体を `Codex CLI（codex exec）のサーバ側非対話実行` とする。
- 解析はキュー経由の非同期実行とし、HTTP リクエスト内で解析完了を待たない。これにより画面リロード後も解析が継続する。
- 既存の Gemini 直結経路と ChatGPT ウインドウ経路は当面併存させるが、**利用者向けの入口は1つに保つ**。どのエンジンで解析するかは運用設定であり、利用者に毎回選ばせる操作にはしない。

**UI方針**
- 部品登録画面のデータシート欄に置く主ボタンは `データシートから自動入力` の1本のみとする。エンジン名（Gemini / ChatGPT / Codex）をボタン名に出さない。
- 解析中表示も1種類に統一する。現行の `Gemini で解析中` `ChatGPT で解析中` のような、内部実装が透けた二重表現は廃止する。
- 解析エンジンの選択は `連携設定` に置く運用設定とし、既定を Codex とする。ChatGPT ウインドウ経路は連携設定で明示的に選んだ場合のみ有効な旧経路として残す。
- `連携設定` に Codex のログイン状態を表示する。トークン失効時は画面上で `再ログインが必要` と判別でき、対処導線を持たせる。Gemini の API キー未設定表示と同じ扱いにする。
- 解析中は部品登録画面をブロックせず、進行状態カードで示す。ページを離れて戻っても状態が復元できることを前提にする。
- `ChatGPTから貼り付け`（手貼り）はフォールバックとして残す。

**フロー案**
1. 利用者が PDF を選び `データシートから自動入力` を押す。
2. サーバは既存の一時PDF保管を行い、解析ジョブを登録して即座に `解析ID` を返す（完了を待たない）。
3. ジョブは token 単位の作業ディレクトリを作り、PDF からテキストを抽出する。テキスト層が十分ならテキストのみを渡す。テキストが不足する（スキャン PDF）場合はページ画像へ変換して添付する。
4. `codex exec` を JSON スキーマ強制で実行し、最終応答を JSON として受け取る。
5. 受け取った JSON を既存の正規化処理とスペック詳細照合へ通し、解析結果として保存する。
6. 画面は解析IDで状態を取得し、完了したら既存の解析候補確認モーダルへ渡す。
7. ジョブ終了時に作業ディレクトリを削除する。

**API方針**
- 解析の登録・状態取得・破棄を分離する。登録は解析IDを返すのみとし、状態取得で `待機中 / 準備中 / 解析中 / 完了 / 失敗` と結果または失敗理由を返す。
- 既存の一時PDFトークンを解析入力として受け取れるようにし、同じ PDF を二重にアップロードさせない。
- 連携設定側に、解析エンジンの取得・変更と、Codex ログイン状態の取得を持たせる。

**prompt と出力契約の扱い**
- `プロンプト/データシート解析プロンプト.md` を引き続き唯一の prompt 正本とする。
- Codex 実行時は最終応答の形を JSON スキーマで強制する。応答本文から JSON を探索・抽出する処理は持たない。現行 userscript が行っているコードブロック剥がしや JSON 有無判定は、この方式では不要になる。
- スキーマは prompt 正本と対で管理し、prompt とスキーマの内容が食い違わないようにする。
- 解析結果の後段（値プロファイル正規化、スペック詳細照合、部品分類候補とテンプレート推薦）は既存処理をそのまま流用する。エンジンを増やしても後段は分岐させない。

**実行環境と隔離方針**
- Web リクエストを処理するプロセスから直接 Codex を起動しない。キュー worker 専用ユーザで実行する。
- Codex の認証情報は自動更新されるため、実行ユーザから書き込み可能な専用の Codex ホームディレクトリを用意する。Web サーバ実行ユーザのホームを流用しない。
- 作業ディレクトリはリポジトリ配下に置かない。リポジトリを作業根に指定すると `AGENTS.md` や `CLAUDE.md` が自動で読み込まれ、解析プロンプトが汚染される。
- 実行はファイル読み取りのみ許可する隔離設定とし、利用者設定やルールファイルの読み込みも抑止して、解析ごとに同じ条件で動くようにする。
- 解析ごとに実行時間の上限を設け、上限超過は失敗として扱う。

**失敗時の扱い**
- Codex 未ログインまたはトークン失効: 解析を開始せず、連携設定へ誘導する。
- 実行時間上限超過: 失敗として記録し、画面から再実行できるようにする。
- 出力がスキーマに適合しない: 1回だけ再実行し、それでも不適合なら失敗として手貼り導線へ誘導する。
- テキスト抽出も画像化もできない PDF: 解析不能として手貼り導線へ誘導する。
- 利用枠の上限到達: 失敗理由を利用枠起因として区別して表示し、時間を置いた再実行を促す。

**実機で確認すべき前提**
- 本番サーバに Codex CLI、Node、PDF 変換ツールが存在するか。
- Codex のログインが本番サーバ上で完了できるか（ブラウザなしの認証手段が使えるか）。
- キュー worker を常駐させる運用が置けるか。
- 実データシート数件での所要時間、抽出精度、利用枠の消費量。

**DB変更の扱い**
- 解析状態を画面リロード後も追跡するため、解析ジョブの状態と結果を保持する新テーブルを追加する。
- テーブル追加は DB 変更に該当するため、`接続先確認 / 件数確認 / バックアップ確認 / 復元手段確認` の4点を記録してから実施する。既存テーブルへの破壊的変更は行わない。

**実装順**
1. 実機前提の確認（Codex CLI、PDF 変換ツール、ログイン、キュー常駐）。
2. サーバ側解析基盤（解析状態テーブル、キュージョブ、解析エンジンの差し替え口）。
3. Codex 実行部（PDF 前処理、スキーマ強制実行、隔離設定、失敗分類）。
4. UI 導線の統合（入口を1本化、解析中表示の統一、連携設定へのエンジン選択とログイン状態表示）。
5. 旧経路の降格（ChatGPT ウインドウ経路を既定から外し、選択時のみ有効な旧経路として残す）。

## 13. DB設計修正（確定）

### spec_types / spec_units / 接頭辞ポリシーの分離

`spec_types` はスペックの意味と基底単位を持つ。`spec_units` は明示的な単位候補や倍率を持つ。加えて、スペック詳細ごとに「候補へ出す接頭辞」「表示時に優先する接頭辞」「表記ゆれ吸収ルール」を設定できるようにする。

単位入力はドロップダウンで縛らず、テキスト入力を基本とする。ドロップダウンや datalist は入力補助であり、保存可否の唯一の基準にしてはならない。

```sql
-- 修正前（誤）
spec_types ( id, spec_name, unit, description )

-- 修正後（正）
spec_types ( id, spec_name, base_unit, description, prefix_policy )
spec_units ( id, spec_type_id (FK), unit_label, factor )
-- 例: spec_type_id=1(voltage) → V, mV
--     spec_type_id=2(resistance) → Ω, kΩ, MΩ
```

#### 接頭辞ポリシー

`prefix_policy` は JSON などの構造化値として持つ。初版は列追加または補助テーブルのどちらでもよいが、UI/API では次の概念を扱えることを要件とする。

| 項目 | 役割 | 例 |
|---|---|---|
| `base_unit` | 正規化先の基底単位 | `Ω`, `A`, `V`, `F`, `Hz` |
| `input_prefixes` | 値欄・インライン単位で許容する接頭辞 | `M,k,,m,u,n,p` |
| `suggest_prefixes` | 値入力の候補や補助に使う接頭辞 | 抵抗値なら `M,k,,m` |
| `display_prefixes` | 表示時の自動逆変換で使う接頭辞 | 電流なら `A,m,u,n` |
| `unit_aliases` | 表記ゆれ吸収 | `Ω -> Ω`, `ohm -> Ω` |
| `prefix_aliases` | 接頭辞ゆれ吸収 | `K -> k`, `µ/μ -> u` |
| `allow_free_unit` | 候補外単位の手入力を許すか | 原則 `true` |

接頭辞ポリシーは入力制限ではなく、主に **候補表示・正規化・表示逆変換の品質を上げるための設定** とする。候補にない `uΩ` が入力されても、`base_unit=Ω` かつ接頭辞として解釈可能なら保存できる。候補外を完全拒否すると、シャント抵抗、リーク電流、RF、小信号などの例外を壊すためである。

ただし `B` / `byte` / `bit` / `bps` 系のスペック詳細は、電圧・電流・抵抗のようなSI単位と同じ接頭辞候補にしてはならない。`B` 系で `m/u/n/p/f` を候補に出す実用性は低く、`M` と `Mi` の意味差も大きいため、接頭辞候補は次のセットから選ぶ。

| 接頭辞セット | 候補 | 用途 |
|---|---|---|
| `decimal_full` | `T`, `G`, `M`, `k`, `無印`, `m`, `u`, `n`, `p`, `f` | 電圧・電流・抵抗・容量・周波数などの通常SI単位 |
| `decimal_non_fractional` | `T`, `G`, `M`, `k`, `無印` | Byte/bit/通信速度など、小数接頭語を候補に出さない10進系 |
| `binary_iec` | `Ti`, `Gi`, `Mi`, `Ki` | Byte系の2進接頭語。`無印` は接頭語ではなく基準単位表示として共通許可 |

スペック詳細編集UIでは、10進数系と2進数系の接頭辞を横断選択させない。`Ti/Gi/Mi/Ki` のいずれかを選んだ場合、`T/G/M/k/m/u/n/p/f` は自動で外す。逆に10進数系を選んだ場合、`Ti/Gi/Mi/Ki` は自動で外す。`無印` は接頭辞グループ外の基準単位表示であり、10進・2進どちらの表示セットでも使える。

`B` / `bit` / `bps` 系では、既定候補は `decimal_non_fractional` または `binary_iec` のどちらかに限定する。2進数系で `m/u/n/p/f` を選べるようにはしない。入力パーサは `Ti/Gi/Mi/Ki` を `T/G/M/k` より先に判定し、`MiB` を `M + iB` のように誤解しない。

代表設定例:

| spec_type | base_unit | suggest/display prefixes | 備考 |
|---|---|---|---|
| 抵抗値 | `Ω` | `M,k,,m` | 候補は実務頻出へ絞る。`uΩ` 等は自由入力で許容 |
| 容量 | `F` | `u,n,p` | `mF` は候補に出してもよいが優先度低 |
| 電圧 | `V` | `k,,m,u` | `K` は接頭辞としては `k` に補正 |
| 電流 | `A` | `,m,u,n` | リーク電流向けに `pA` も設定可 |
| 周波数 | `Hz` | `G,M,k,` | `KHz` は `kHz` に補正 |
| フラッシュ容量 | `B` | `G,M,k,` または `Gi,Mi,Ki,` | 10進系と2進系は同時選択不可。`mB/uB` は候補に出さない |
| RAM容量 | `B` | `Gi,Mi,Ki,` | 2進表示を優先する場合。`B` は無印の基準単位 |
| 通信速度 | `bps` | `G,M,k,` | 原則10進系。`m/u/n/p/f` は候補に出さない |
| 温度 | `°C` | なし | 接頭辞を使わない |
| 許容差型 | `%` / `ppm` / `pF` / `ppm/℃` / コード | なし | 通常の共通スペック詳細とは別棚の許容差スペック詳細として扱う。例: 抵抗値許容差 `±5%`、容量許容差 `B級 ±0.1pF`、容量許容差 `Z級 +80/-20%`、抵抗温度係数 `±100ppm/℃`、容量温度特性 `X7R` |
| チャンネル数 | `ch` | なし | 接頭辞を使わない |

### component_specs の数値表現を「人間向け表示 + value_profile + 基底単位正規化」へ再設計

#### なぜ変えるか

従来の `component_specs.value_numeric` 単独方式は、`数値検索のための裏値` と `人が見る値` を無理やり 2 列へ押し込んでいたため、次の問題を抱えていた。

1. `1uA` と入力したいのに、検索都合で `0.000001` を別欄へ手入力させる必要がある  
2. `2〜5V` のような範囲値を自然に扱えない  
3. 保存された `value` が人間向け表示、`value_numeric` が検索用内部値という二重構造になり、入力・表示・検索の意味がズレやすい  
4. `1e-6A` で検索しても、表示が `1uA` のデータと整合しないケースが起きやすい  

電子部品のデータシートと人間の作業導線は `uA / mA / kΩ / ns` のような接頭語付き表記を前提にしている。したがって BitsKeep も、**入力は人間に合わせ、内部比較だけを基底単位へ統一する** 方針へ切り替える。

ただし、`single / range + 中央値` だけで全部を表す設計も不十分である。電子部品のデータシートでは、`typ` は代表値、`min/max` は保証境界や条件端であり、意味が違う。たとえば `typ=5mA, max=10mA` を単純な `5〜10mA` の範囲に潰すと、設計時に不要なマージンを要求したり、逆に typ を保証値のように誤読したりする。

そのため、BitsKeep では **`null の入り方で意味を推定しない`**。スペックの意味は `value_profile` で明示し、数値列はその profile に従って埋める。

#### 採用方針

- 入力:
  - 人は `1uA` 相当の値を、`value=1u` `unit=A` のように、接頭語を値側、単位を基準単位側に分けて入力する
  - 値の意味は `value_profile` で明示選択する
  - profile は `typ / range / max_only / min_only / triple` の5種とする
- 内部保存:
  - すべて `spec_types.base_unit` に正規化して保存する
  - 例: `1uA -> 0.000001 A`、`10kΩ -> 10000 Ω`
- 表示:
  - 保存後は内部値から最も読みやすい接頭語へ戻して表示する
  - 例: `0.000000001 A -> 1nA`
- 検索:
  - 検索時も同じ正規化ルールを通し、入力単位に依存しない比較を行う
  - ただし `typ / range / max / min` は意味が違うため、検索も profile を意識して照合する

#### value_profile の定義

| `value_profile` | 意味 | 埋める列 |
|---|---|---|
| `typ` | 1点の代表値 | `value_numeric_typ` |
| `range` | 最小〜最大の範囲 | `value_numeric_min`, `value_numeric_max` |
| `max_only` | 上限のみ | `value_numeric_max` |
| `min_only` | 下限のみ | `value_numeric_min` |
| `triple` | min / typ / max の3値 | `value_numeric_min`, `value_numeric_typ`, `value_numeric_max` |

`min/max/typ` の `NULL` パターンだけで profile を推定してはならない。  
判定の正本は常に `value_profile` とする。数値列の `NULL` は「その意味の値を持たない」ことだけを表す。

#### DB 変更方針

既存データを消さず、`component_specs` に列追加で移行する。現行の `value_mode` / `value_numeric` は第1段階実装の互換列として残っているが、最終的な正本は以下へ移す。

```sql
component_specs (
  id,
  component_id (FK),
  spec_type_id (FK),
  value,              -- 人が見る値。例: "1" / "2 〜 5"
  unit,               -- 人が見る表示単位。例: "uA" / "V" / "kΩ"。編集UIでは基準単位へ寄せる
  value_profile,      -- "typ" / "range" / "max_only" / "min_only" / "triple"
  value_numeric_typ,  -- typ値（基底単位）
  value_numeric_min,  -- 最小値（基底単位）
  value_numeric_max,  -- 最大値（基底単位）
  normalized_unit     -- 基底単位。例: "A" / "V" / "Ω"
)
```

#### 各列の役割

| 列 | 役割 | 例 |
|---|---|---|
| `value` | 人が読む表示値 | `1` / `2 〜 5` / `1 / 5 / 10` |
| `unit` | 人が読む表示単位。編集UIでは基準単位へ寄せる | `uA` / `kΩ` / `ns` |
| `value_profile` | 値の意味を明示する列 | `typ` / `max_only` / `triple` |
| `value_numeric_typ` | 代表値（基底単位） | `0.000001` / `5` |
| `value_numeric_min` | 下限値（基底単位） | `2` / `0.0008` |
| `value_numeric_max` | 上限値（基底単位） | `5` / `10` |
| `normalized_unit` | 内部比較に使う基底単位 | `A` / `V` / `Ω` |

#### 正規化ルール

登録・更新時はサーバー側で以下を自動計算する。クライアントから送られた内部値は信用せず、毎回再計算する。

| spec_type | 基準単位 | 入力例 | 内部値 |
|---|---|---|---|
| resistance | Ω | `10kΩ` | `10000 Ω` |
| voltage | V | `100mV` | `0.1 V` |
| current | A | `50mA` | `0.05 A` |
| power | W | `500mW` | `0.5 W` |
| frequency | Hz | `16MHz` | `16000000 Hz` |
| time | s | `5ns` | `0.000000005 s` |
| memory_size | B | `1MB` / `1MiB` / `512KiB` | `1000000 B` / `1048576 B` / `524288 B` |
| data_rate | bps | `1Mbps` | `1000000 bps` |

互換のため、値欄・単位欄のどちらに接頭辞が入っても同じ内部値へ正規化する。ただし編集UIでは、スペック詳細が選択されている通常スペックの単位欄は `spec_types.base_unit` へ固定し、接頭辞は値欄へ寄せる。
`B` / `bit` / `bps` 系のスペック詳細は、候補接頭辞を `decimal_non_fractional=T/G/M/k/無印` と `binary_iec=Ti/Gi/Mi/Ki` に分ける。マスタ管理UIでは `Ti/Gi/Mi/Ki` も通常選択肢として表示し、一方のグループを選んだらもう一方を自動で外す。`/api/spec-types` は、10進接頭辞と IEC 接頭語の同時選択を禁止し、`m/u/n/p/f` は Byte/bit 系の候補にしない。`MiB` / `GiB` などの IEC 接頭語は、`M` / `G` などの10進接頭辞より先に判定する。

| 入力値 | 入力単位 | spec_type.base_unit | 内部値 |
|---|---|---|---|
| `1` | `kΩ` | `Ω` | `1000 Ω` |
| `1k` | `Ω` | `Ω` | `1000 Ω` |
| `1kΩ` | 空欄 | `Ω` | `1000 Ω` |
| `1KΩ` | 空欄 | `Ω` | `1000 Ω` |
| `1MEGΩ` | 空欄 | `Ω` | `1000000 Ω` |
| `0.001` | `MΩ` | `Ω` | `1000 Ω` |
| `1u` | `A` | `A` | `0.000001 A` |
| `1µA` | 空欄 | `A` | `0.000001 A` |

正規化パーサは `spec_types.prefix_policy` を参照し、文脈に応じて表記ゆれを吸収する。実装上の正本はフロント側 `resources/js/utils/engineeringUnits.js` とサーバ側 `App\Support\EngineeringUnits` に置き、設計解析ツール、エンジニア電卓、抵抗網、部品シリーズ、スペック詳細APIはここを使う。たとえば抵抗値・電圧・電流・周波数では `K` を `k`、`µ/μ` を `u`、`meg/MEG` を `M` 相当として扱ってよいが、温度やバイト系の値では無条件に同じ補正をしてはならない。未知接頭辞は画面候補から除外し、API保存時はバリデーションエラーにする。

表示時は `value_numeric_* + normalized_unit` を、同じポリシーの `display_prefixes` で人間向け表記へ戻す。`1000000 Ω` のような表示は避け、抵抗値なら `1MΩ`、電流なら `1uA` のように表示する。既存データや外部入力で `kΩ` / `uA` のような接頭語付き単位が来た場合は、編集UIへ載せる時点で `value=1k` `unit=Ω` の形へ寄せる。

#### スペック詳細の粒度とprofile表示

UI表示では `spec_types` を **スペック詳細** と呼ぶ。`spec_types` は「検索・比較したい仕様項目」を保持する内部テーブルである。粒度の基準は下記の通り。

- **粗すぎる（不可）**: `電流 [A]` — 単位と意味が重なり、`コレクタ電流` `ベース電流` を区別できない
- **細かすぎる（不可）**: `最大コレクタ電流` — `value_profile=max_only` と重複し、マスタが際限なく増殖する
- **適切**: `コレクタ電流`、`パルスコレクタ電流`、`コレクタ-ベース間電圧`、`直流電流増幅率` — 仕様項目単位

`value_profile` の違い（max/min/typ）は **`spec_type` を分裂させず、`value_profile` で表現する**。  
`コレクタ電流` と `パルスコレクタ電流` のように検索・比較で別軸にしたい項目は、別 `spec_type` として持つ。

`spec_types` は日本語名・英語名・記号を持ち、表記ゆれは alias で吸収する。`name_ja` は表示名であり、一意制約を持たせない。例: `電源電圧` を `VDD` / `VCC` で別 `spec_type_id` として持てるようにし、区別は `symbol` / alias / 文脈で行う。

現時点では UI 表示名だけを `スペック詳細` へ変更し、DB/API/コード内部名は `spec_types` / `spec_type_id` / `/api/spec-types` のまま残している。これは意図した短期対応だが、表示名と内部名がずれる設計負債である。将来、モデル・API・仕様書の内部用語まで改名するか、用語表で「スペック詳細 = spec_types」と固定する判断が必要である。

```sql
spec_types (
  id,
  name,            -- 互換用。原則 name_ja と同じ値を入れる。一意ではない
  name_ja,         -- 表示日本語名。一意ではない
  name_en,         -- 英語名
  symbol,          -- h_FE, V_CBO, V_CE-(sat) など。_ は下付き、~ は上付き、- は通常表示へ戻す区切り
  suggest_prefixes, -- 入力候補接頭辞 JSON配列。null=汎用SI候補
  display_prefixes, -- 表示逆変換接頭辞 JSON配列。null=自動選択
  spec_scope,      -- common / group_local。共通スペック詳細か主所属を持つスペック詳細かを示す
  spec_kind,       -- normal / tolerance。通常スペック詳細か許容差スペック詳細かを示す
  tolerance_settings, -- 許容差型の既定入力設定 JSON。default_mode/default_unit/allowed_units/grade_options 等
  owner_spec_group_id, -- group_local の主部品分類。common は null

  description,
  sort_order
)

spec_type_aliases (
  id,
  spec_type_id,
  alias,      -- VCBO, Collector Base Breakdown Voltage 等
  locale,
  kind,
  sort_order
)

  id,
  name,        -- BJT / MOSFET / OPアンプ / マイコン 等。共通はここへ置かない
  description,
  sort_order,
  deleted_at
)

spec_group_spec_type (
  id,
  spec_group_id,
  spec_type_id,
  sort_order,      -- 部品分類内の表示順
  is_required,     -- テンプレート適用時に必須扱いする候補
  is_recommended,  -- 通常候補として上位に出す

spec_templates (
```

#### 部品分類と入力テンプレート

`部品分類` は部品そのものに付ける種類・検索タグであり、同時にスペック詳細の候補・分類内順序・必須/推奨・既定profile・既定単位を束ねる入力候補グループでもある。UI 上は `部品分類` と呼び、DB/API は互換名のまま `spec_groups` とする。

旧 `categories` と `/api/categories` は廃止する。既存の `component_category` は `component_spec_group` へ移行し、旧 `category_spec_group` がある分類はリンク先の `spec_groups` へ部品紐付けを付け替える。リンクがない旧分類は同名の `spec_groups` を作成または再利用して吸収する。部品分類の取得・登録・更新・アーカイブ・復元は `/api/spec-groups` に統一する。

スペック詳細は `spec_types` で保持する。部品分類に主所属を持つスペック詳細は `spec_types.spec_scope='group_local'` とし、主に整理する部品分類を `owner_spec_group_id` へ持つ。`group_local` は「この部品分類専用」ではなく、運用上の主所属を示す。専用表示をする場合は owner 以外の部品分類へ紐付けない制約が必要だが、今回はその制約を置かず主所属表現へ寄せる。複数部品分類で横断的に使うスペック詳細は `spec_types.spec_scope='common'` とし、`spec_groups` に `共通` という部品分類を作らない。

通常の共通スペック詳細と許容差スペック詳細は兄弟の別棚として扱う。内部データはどちらも `spec_types` のまま維持し、内部種別は `spec_kind=normal/tolerance` で区別する。許容差スペック詳細は `tolerance_settings` に `default_mode`、`default_unit`、`allowed_units`、`grade_options` などを持てる。代表例は `抵抗値許容差 ±5%`、`容量許容差 B級 ±0.1pF`、`容量許容差 Z級 +80/-20%`、`抵抗温度係数 ±100ppm/℃`、`容量温度特性 X7R`、`周波数許容差 ±20ppm` とする。許容差を「%単位で接頭辞なし」と固定せず、%・ppm・pF・ppm/℃・コード・等級・非対称範囲を扱える許容差型として設計する。

画面上は `部品分類 -> スペック詳細` の選択として見せる。DB上は `spec_groups` と `spec_group_spec_type` の多対多で表現し、部品分類内の並び順・必須/推奨・既定profile・既定単位は pivot 側に持たせる。

`spec_group_spec_type` は、主所属を持つスペック詳細では「その部品分類の候補として持つ」関係、共通スペック詳細・許容差スペック詳細では「この部品分類の候補に入れる/候補から外す」関係として扱う。`候補から外す` はスペック詳細そのものを削除する操作ではなく候補関係の解除であり、確認ダイアログを挟んでから自動保存する。スペック詳細そのものを使わなくする操作は各スペック詳細タブの `アーカイブ` に統一する。共通スペック詳細・許容差スペック詳細そのものの編集は各タブの `編集` で行い、部品分類内の扱い・既定値・メモは `スペック候補設定` の `編集` で行う。

スペック編集UIは説明文や分類カードで理解させるのではなく、`部品分類`、`スペック候補`、`入力テンプレート`、`登録済みスペック` の構造で操作対象を分ける。`部品分類` は select とし、選択肢はマスタ上の部品分類と `フィルタしない` とする。部品詳細のスペック編集では、当該部品に登録済みの部品分類を初期選択する。返却する候補は選択中 ID に紐づく候補を基本とする。`フィルタしない` の場合だけ候補を部品分類で絞らず、手動補正用に広く探せる状態にする。共通スペック詳細・許容差スペック詳細も、選択中部品分類の `spec_group_spec_type` に採用されているものだけを分類フィルタ時の通常候補として返す。

`スペック候補` は dropdown と `追加` ボタンで1行追加する導線にする。候補にない個別スペック詳細は、既存候補/テンプレート追加領域の下に罫線を引いた別段として置く `スペックを新規で追加` から追加する。`追加` と横並びにせず、登録済みスペック行を追加する主操作と、スペック詳細マスタを作成する例外操作を視覚的に分ける。`入力テンプレート` は dropdown と `一式追加` ボタンで複数行を追加する導線にし、テンプレート選択時は `[ピーク耐圧 V_RRM]` のように、実際に一括追加されるスペック詳細の日本語名と略号をチップでプレビューする。単なる「x項目」表示だけにはしない。追加済みの行は下部の `登録済みスペック` に並べ、既に同じスペック詳細がある行は重複追加しない。

`スペックを新規で追加` のモーダルでは、単位欄を `基準単位` として表示する。ここには `F` / `Ω` / `A` のような基底単位だけを入力し、`uF` / `kΩ` / `mA` のような接頭語付き単位を候補例として出さない。値入力で使える `u` / `k` / `m` などは `入力候補接頭辞` として常時選択できるようにし、基準単位欄に誤って接頭語付き単位が入力された場合も保存前に基底単位へ寄せ、接頭語候補へ補完する。

部品詳細からマスタ管理へ移動する導線は、選択中の部品分類を `group_id` として引き継ぐ。`スペック詳細` は個別スペック詳細の作成・編集、`スペック候補設定` は個別/共通/許容差の採用と既定値、`共通スペック詳細` と `許容差スペック詳細` は横断項目そのものの編集、`入力テンプレート` は複数スペック行のセット管理を担当する。登録済みスペック行には未登録スペック詳細作成の `+` を置かない。登録済み行は既存スペック詳細の割り当て、値種別、値、単位、確認だけを扱う。

#### 部品シリーズと値展開ポリシー

抵抗、コンデンサ、インダクタのように、同じシリーズ・同じパッケージ・同じ許容差・同じ定格で値だけが大量に展開される部品は、`components` を値の数だけ直接作るのではなく、上位に **部品シリーズ** を置く。`部品シリーズ` は「どの部品分類の、どの代表スペック詳細を軸に、どの値候補を持つか」を管理する単位である。実際に在庫・商社・型番・データシートを持つ必要が出た値だけを `components` として部品化する。

IC、MCU、FPGA、OPアンプ、センサIC、モジュールのように、値の1軸展開より型番ごとの機能差・ピン配置・世代差が支配的な部品は、従来通り部品単位登録を基本とする。メーカーの商品ファミリが存在しても、在庫管理・比較・検索の主軸が単純な値展開でないものは `部品シリーズ` に寄せない。

`部品分類` は検索タグと候補スペック詳細の束、`スペック詳細` は仕様項目、`候補スペック詳細` は部品分類内の入力候補、`共通スペック詳細` と `許容差スペック詳細` は横断的な項目棚である。`部品シリーズ` はこれらを置き換えない。部品シリーズは必ず1つの主 `部品分類` と、値展開軸になる1つの代表 `スペック詳細` を参照する。例: チップ抵抗シリーズは `部品分類=抵抗`、代表スペック詳細=`抵抗値`、容量シリーズは `部品分類=コンデンサ`、代表スペック詳細=`静電容量`、水晶シリーズは `部品分類=発振子`、代表スペック詳細=`クロック周波数` を持つ。

**シリーズ管理が向く対象例:**

| 対象 | 値展開軸の例 | 備考 |
|---|---|---|
| 抵抗 | 抵抗値 | 許容差・温度係数・定格電力・サイズはシリーズ共通または値別上書き |
| コンデンサ | 静電容量 | 許容差、温度特性、耐圧、サイズを組み合わせる |
| インダクタ / フェライトビーズ | インダクタンス、インピーダンス | 定格電流・直流抵抗は値別上書きが出やすい |
| ツェナー / TVS | ツェナー電圧、逆方向スタンドオフ電圧 | E系列前提にしない任意値リストが基本 |
| 水晶 / 発振器 | クロック周波数 | 32.768kHz、12MHz、25MHz 等の任意値を正式に扱う |
| ヒューズ / PTC | 定格電流、保持電流 | E系列ではなくメーカー系列・安全規格の値並びを優先 |
| ピンヘッダ / コネクタ | 極数、ピン数、ピッチ | 範囲/刻みまたは任意値リストで扱う |
| LED | 発光色、波長、光度ランク | 値軸が複数になる場合は部品化を優先し、シリーズは補助に留める |

**単体登録を基本にする対象例:**

| 対象 | 理由 |
|---|---|
| MCU / FPGA | 型番ごとの周辺機能、メモリ、ピン配置、世代差が支配的 |
| OPアンプ / コンパレータ | 回路数、電源範囲、速度、入力形式、出力形式など複数軸で差が出る |
| センサIC | 測定対象、インタフェース、校正、パッケージ差が支配的 |
| モジュール | 外形、ピン配置、付属回路、ファーム差分が主軸 |

**値展開ポリシー:**

| 種別 | 用途 | 破綻させないための扱い |
|---|---|---|
| `e_series` | E6 / E12 / E24 / E48 / E96 などに素直に乗る値展開 | 基準系列、開始値、終了値、0Ω追加有無、単位、丸め桁を持つ |
| `hybrid_series` | E12中心だが一部だけE24や手動値が混ざる実運用 | 基準系列、追加系列、追加値を同じシリーズ内に持つ。追加値があるだけで別シリーズへ分裂させない |
| `custom_list` | ツェナー電圧、水晶周波数、ヒューズ電流、コネクタ極数など非E系列 | 任意値リストを正として持つ。E系列生成器を通さない |
| `range_step` | 1x02から1x40ピン、0.5A刻み等の範囲/刻み | 最小・最大・刻み・除外値・表示ラベルを持つ |
| `none` | 値展開しないシリーズ、またはシリーズを使わない部品分類 | 部品登録を従来通り優先し、シリーズは使わない |

部品シリーズでは、部品分類を選ぶと `スペック詳細` 候補をその部品分類の候補に絞る。単位は選択したスペック詳細の標準単位から自動反映し、シリーズ画面では直接編集させない。パッケージは `パッケージ分類` と `パッケージ詳細` の2段階で選ぶ。

E系列の範囲は、画面では `開始値` / `終了値` として見せる。`1`、`0.1`、`1k`、`10G` のような実数入力を受け、内部では生成に必要なデケード範囲へ変換したうえで、実際の開始値・終了値から外れた候補を落とす。0ΩはE系列の生成対象ではないため、`generation_settings.include_zero` の `0を含む` で追加する。`range_step` はE系列とは別方式で、開始値・終了値・刻み幅を `0`、`10G`、`100M` のような実数入力として扱う。

`hybrid_series` では「保有値はE12でそろえているが、少量だけE24の値が混在する」状態を正常系として扱う。値候補ごとに `由来` を持ち、基準系列から生成された値、追加系列由来の値、手動追加値、CSV取込値、商社取込値を区別する。画面では `E12`、`追加`、`E24`、`手動`、`取込` のような由来バッジを出し、検索・在庫・部品化では同じシリーズ内の値として扱う。

非E系列の値は例外扱いにしない。ツェナー電圧の `2.4V / 2.7V / 3.0V / 3.3V`、水晶周波数の `32.768kHz / 8MHz / 12MHz / 16MHz / 24MHz / 25MHz`、ヒューズ電流の `0.5A / 0.75A / 1A / 1.25A`、コネクタ極数の `2 / 3 / 4 / 6 / 8 / 10 / 20 / 40` は、`custom_list` または `range_step` の正式な値候補として持つ。ソートは数値化できる場合は正規化値、できない場合は `sort_order` と表示ラベルを正とし、E系列のデケード順を前提にしない。

現行実装では値別上書きテーブルはまだ切らず、値候補の部品化時に `components` と `component_specs` を作る。コンデンサの高容量だけサイズが変わる、インダクタの値によって定格電流や直流抵抗が変わる等の値別差分は、部品化済み `components` 側のスペックとして扱う。

部品分類は内部値として `series_management_mode = single / series_optional / series_recommended` を持つ。UIでは `シリーズを使わない`、`シリーズ登録も使う`、`シリーズ登録を推奨` と表示する。`single` の分類は従来通り `components` 登録を主導線にし、`series_optional` / `series_recommended` の分類は `/component-series` から値マトリクスを作って必要な値だけ実部品化する。

部品登録画面には `登録単位` を置き、`単体` と `シリーズ` を明示的に切り替える。`単体` は従来通り `components` だけを正本にする。`シリーズ` を選んだ場合だけ `component_series_id` と `component_series_value_id` を入力対象にし、登録する実部品を部品シリーズ内の値候補へ紐づける。
`シリーズ` は既存の `component_series` / `component_series_values` への紐づけ導線であり、部品登録フォーム内で部品シリーズや値マトリクスを新規作成しない。登録済みシリーズが0件の場合は空の select を出さず、`部品シリーズ未登録` と `マスタ・利用設定 > 部品シリーズ` への遷移を表示する。

**UI案:**

- 部品シリーズ詳細は、上部に `部品分類`、`シリーズ名`、`スペック詳細`、`パッケージ詳細`、`メーカー`、`値候補の作り方` を出す
- 値展開ポリシーは `E系列`、`基準系列+追加値`、`任意値リスト`、`範囲/刻み`、`値展開なし` から選ぶ
- `基準系列+追加値` では `基準系列=E12`、`追加系列=E24`、`追加値=75kΩ, 91kΩ` のように同じシリーズ内で混在を管理する
- `任意値リスト` では、1行1値またはCSV貼り付けで値を投入し、単位・表示ラベル・並び順を編集できる
- シリーズ詳細の下段は値マトリクスにする。列は `値`、`由来`、`部品化状態`、`在庫`、`パッケージ`、`商社型番`、`値別上書き`、`メモ` を基本とする
- 由来は `E12`、`追加`、`E24`、`手動`、`取込` のバッジで表示する
- E系列・範囲/刻みの `開始値` / `終了値` / `刻み幅` は、選択したスペック詳細の `suggest_prefixes` に従う。容量で `u/n/p/f` が候補なら `1fF`、`10pF` を受け付け、候補外の接頭語はバリデーションエラーにする。画面上の接頭語説明も選択中スペック詳細から動的に表示し、固定の `k/M/G` 文言は使わない
- 操作は `値を追加`、`E系列から生成`、`CSV貼り付け`、`選択値を部品化`、`無効化` に分ける。`選択値を部品化` は保存済み・未部品化・有効な値だけ選択可能にし、押せない理由をボタン付近に表示する
- 値マトリクス上では、未部品化の候補値と実部品化済みの値を同じ表で見せるが、通常の部品一覧には実部品だけを出す

**検索・在庫・部品化方針:**

- `component_series_values` は候補値であり、在庫実体ではない。通常の部品一覧、在庫一覧、入出庫は `components` と `inventory_blocks` を正とする
- 値候補を通常一覧にそのまま展開しない。未保有のE系列値や任意値が大量に見えて、実在庫の検索性を壊すため
- シリーズ詳細、部品登録補助、設計探索では、未部品化の値候補も表示できる。表示時は `候補値` と `実部品` を明示する
- `選択値を部品化` すると `components` を作成し、代表スペック詳細の `component_specs`、部品分類、パッケージ、シリーズへの逆参照を付与する
- 既に部品化済みの値は重複作成せず、既存 `components` へリンクする
- 合成抵抗/容量探索などの計算ツールでは、`在庫あり` モードは実部品化済みかつ在庫ありの値だけを使う。`候補値込み` モードを別に用意する場合も、結果に候補値であることを明示する

**既存部品からの移行手順:**

1. 同一メーカー、シリーズ名、部品分類、パッケージ、許容差、温度特性で既存 `components` を候補グループ化する。
2. 値軸スペック詳細（抵抗値、静電容量、周波数など）を読み、`component_series_values.value_numeric / value_text / unit` へ抽出する。
3. 在庫、仕入先、画像、データシートを持つ既存部品は削除せず、該当値候補の `materialized_component_id`、および `components.component_series_id / component_series_value_id` を設定する。
4. 同値・同パッケージで複数候補が出たもの、値軸が読み取れないもの、メーカーシリーズ名が曖昧なものは確認リストへ残し、手動でリンクする。
5. 移行後も通常の部品一覧と在庫管理は `components` を正とし、未部品化の候補値は `/component-series` の値マトリクスでのみ扱う。

#### profile のバッジ表示

`value_profile` は項目名に **前置き合成しない**。`最大コレクタ電流` のような合成文字列は生成しない。

理由: 画面に出る文字列がマスタに存在しないと、3年後の自分がマスタを探して見つからず混乱する。UIの構造がそのまま仕様の説明になっている設計を優先する。

| spec_type.name | profile | 表示 |
|---|---|---|
| `コレクタ電流` | `typ` | `コレクタ電流` |
| `コレクタ電流` | `max_only` | `コレクタ電流` + `[MAX]` バッジ |
| `コレクタ電流` | `min_only` | `コレクタ電流` + `[MIN]` バッジ |
| `コレクタ電流` | `range` | `コレクタ電流` + `[MIN..MAX]` バッジ |
| `コレクタ電流` | `triple` | `コレクタ電流` + `[MIN/TYP/MAX]` バッジ |

バッジは項目名の右横に小さく添える。詳細・一覧・編集モーダルで共通。

#### UI 方針

- 登録画面 / 詳細編集:
  - スペック行の自由な `名前` 入力欄は置かない。保存時は `spec_type_id` でスペック詳細へ紐付ける
  - 値種別は行内の5分割ボタンではなく、`TYP`、`MIN..MAX`、`MAX`、`MIN`、`MIN/TYP/MAX` の短いセレクトで選ぶ
  - `スペック詳細` は全件ドロップダウンではなく、部品分類に紐づく候補スペック詳細と、その部品分類へ採用済みの共通スペック詳細・許容差スペック詳細を出す検索ピッカーで選択する
  - 詳細編集では、対象部品の部品分類から `GET /api/spec-suggestions` を呼び、モーダル上部に部品分類ボタンと部品分類内検索を出す。各行の `select` へ全件を流さず、選択中部品分類・検索語で絞った候補だけを表示する
  - 既に保存済みのスペック詳細は、現在の部品分類や検索語から外れていても編集中の行の候補に残し、保存済み値を見失わないようにする
  - 候補に無い場合は、部品分類が一意に決まるときだけ、罫線で区切った下段の `スペックを新規で追加` からスペック詳細追加モーダルを開く
  - モーダルで追加したスペック詳細は `spec_scope=group_local` と `owner_spec_group_id` を持つ項目として作成し、即座にその部品分類の候補へ反映して登録済みスペック行へ追加する。同名の既存スペック詳細に一致した場合は新規作成せず、選択中部品分類の候補関係を補完してから登録済みスペック行へ追加する。複数部品分類で主所属が曖昧な場合は、先に部品分類を1つ選ばせる
  - スペック詳細追加モーダルの `基準単位` は基底単位だけを扱う。接頭語付き単位を例示せず、値入力で使える接頭語は `入力候補接頭辞` で選ばせる
  - 上部は `部品分類` select、`スペック候補` dropdown + `追加`、`入力テンプレート` dropdown + `一式追加` を既存候補/テンプレートからの行追加領域として置く。その下に罫線を引き、`スペックを新規で追加` を1ボタンだけ置く。下部に `登録済みスペック` 行を並べ、行内に未登録スペック詳細作成の `+` は置かない
  - `部品分類` の選択肢は、マスタ上の部品分類と `フィルタしない` とする。`候補を絞る部品分類` のような説明文ラベルは使わない
  - `スペック候補` は選択中部品分類で候補スペック詳細を絞り、`追加` で1行生成する。`フィルタしない` の場合は部品分類で絞らず手動補正できる
  - `入力テンプレート` は選択中部品分類に紐づくテンプレートだけを出し、`一式追加` でテンプレート行を一括生成する。テンプレートプレビューは `[ピーク耐圧 V_RRM]` のような実項目チップで表示し、件数だけにしない
  - 値種別はセレクトで `TYP / MIN..MAX / MAX / MIN / MIN/TYP/MAX` を明示選択する
  - 選択した profile に応じて入力欄を切り替える
  - 通常スペックの単位欄は選択したスペック詳細の基準単位を表示し、接頭語候補のドロップダウンは出さない。`k` `u` `n` などは値欄へ入力する
  - `数値化` 手入力欄は廃止し、`基底単位換算` を自動表示へ変える
  - 値欄・単位欄の入力中に、解釈結果を小さなプレビューとして即時表示する
  - プレビューには少なくとも `基底値` と `表示値` を出す。例: `基底: 1000 Ω / 表示: 1kΩ`
  - パース不能、候補外単位、接頭辞の曖昧さがある場合は、保存前に同じ場所へ控えめな警告を出す
- 解析候補レビュー:
  - AIの抽出名は補助表示に留め、保存先のスペック詳細名にはしない
  - `name_ja / name_en / symbol / alias` と既存 `spec_types` を照合し、同じ意味の日本語・英語・略記号を同じ `spec_type_id` へ寄せる
  - `値 / 単位 / スペック詳細` に加えて `value_profile` と `基底値` プレビューを表示する
  - 適用前に `typ / range / max / min / triple` を確認・修正できるようにする

#### AI抽出での修飾語処理方針

データシートはメーカー横断で表記ゆれがある。同一の概念が `コレクタ最大電流`、`最大コレクタ電流`、`Collector Current (max)`、`I_C(max)` のように記述される。

**プロンプト側での強制分離（主防線）：**  
抽出プロンプトで「最大/最小/Max/Min/定格/連続/パルス等の境界条件修飾語を項目名から除去し、`value_profile` と `condition` に振り分けて返せ」と明示指示する。

```
入力: "コレクタ最大電流 200mA"
出力: { name: "コレクタ電流", value_profile: "max_only", value: "200m", unit: "A" }
```

**マッチング層での自動救済（副防線）：**  
`SpecTypeMatchingService` の照合失敗時、修飾語（最大・最小・Max・Min・定格等）を除去した正規化名で再照合し、ヒットした場合は自動的に該当スペック詳細へ寄せ `value_profile` を補正する。人間の判断を挟まず自動適用する。二重登録（`コレクタ最大電流` と `コレクタ電流` が別スペック詳細として並存）をシステムが防ぐ。
- 表示画面:
  - 詳細・比較・一覧で出す値は人間向け表記を優先する
  - 内部の基底値は検索・比較・補助情報に使う

#### UI 入力切替の詳細

| profile | UI 入力欄 |
|---|---|
| `typ` | `typ` 1欄 |
| `range` | `min` + `max` |
| `max_only` | `max` 1欄 |
| `min_only` | `min` 1欄 |
| `triple` | `min` + `typ` + `max` |

選択中の profile に応じて、確認欄のバッジ表示が `[MAX]` `[MIN]` `[MIN..MAX]` `[MIN/TYP/MAX]` へ即時切り替わる。前置き合成（`最大コレクタ電流` のような文字列生成）は行わない。

#### リアルタイム正規化プレビュー

スペック入力欄は自由テキストを許容するため、入力中に「システムがどう解釈したか」を必ず近接表示する。これは説明文ではなく、入力結果の状態表示として扱う。

表示例:

| 入力値 | 単位 | プレビュー |
|---|---|---|
| `1k` | `Ω` | `基底: 1000 Ω / 表示: 1kΩ` |
| `1KΩ` | 空欄 | `基底: 1000 Ω / 表示: 1kΩ` |
| `4.7u` | `F` | `基底: 0.0000047 F / 表示: 4.7uF` |
| `1000000` | `Ω` | `基底: 1000000 Ω / 表示: 1MΩ` |

プレビューは登録画面、部品詳細のスペック編集、解析候補レビュー、パラメータ検索の詳細条件で共通のコンポーネントにする。バックエンド保存時の `SpecValueNormalizerService` と、フロントプレビューのパーサは同じ仕様に従い、保存後にプレビューと実保存値が食い違わないようにする。

#### 既存データの移行

既存行は削除しない。移行は必ず加算 migration で行い、現在の `component_specs` 内容を失わないことを最優先とする。

移行ルールは以下とする。

- 旧 `single` 行、および旧 `value_numeric` しか持たない行:
  - `value_profile = 'typ'`
  - `value_numeric_typ = 旧 value_numeric`
  - `value_numeric_min = NULL`
  - `value_numeric_max = NULL`
- 旧 `range` 行:
  - `value_profile = 'range'`
  - `value_numeric_typ = NULL`
  - `value_numeric_min = 旧 value_numeric_min`
  - `value_numeric_max = 旧 value_numeric_max`
- `normalized_unit` は `spec_types.base_unit` があればそれを使い、無ければ既存 `unit` を保持する
- 旧 `value_mode` / `value_numeric` は移行完了まで互換列として残してよいが、新規ロジックの判定正本には使わない

これにより、**今あるデータを消さずに** 新旧ロジックを共存させたまま段階的に移行できる。

**2026-04-27 深掘り: 設計解析ツールの完成定義**

設計解析ツールは「公式の置き換え」ではなく、設計者が次の判断を早く安全に行うための画面とする。従って、単発計算値だけの状態は `L0: 参考計算` とし、完成扱いにしない。

| レベル | 状態 | 完成扱い |
|---|---|---|
| L0 | 入力値から公式計算値だけを返す | 不可 |
| L1 | `PASS/WARN/FAIL/CHECK` と margin、不足条件、次アクションを返す | 暫定可 |
| L2 | min/typ/max、温度、公差、定格ディレーティングなど最悪条件を扱う | 可 |
| L3 | BitsKeep内の部品候補・在庫候補・案件に接続する | 可 |
| L4 | 解析条件を案件・部品に保存し、再計算・差分比較できる | 理想 |

**共通出力モデル:**
- `verdict`: `PASS` `WARN` `FAIL` `CHECK`
- `summary`: 設計者向けの短い判断文。WARN/FAIL/CHECKでは、`warnings` または `missingConditions` から違反パラメータ、不足条件、基準超過内容を先頭に昇格し、「どれかが確認必要」のような曖昧な要約にしない
- `metrics`: 判定に使った主要数値。単位・条件付き。
- `margin`: 閾値との差分。電圧、電流、温度、時間、% などツール別。
- `dominant_factors`: 支配要因。例: `Vref` `Rs` `起動順` `TVS定格`
- `warnings`: 条件不足、モデル外の注意、データシート確認事項
- `next_actions`: 次に直す/確認する具体行動
- `assumptions`: 仮定値、データシート条件、温度条件、波形条件
- `candidate_links`: 部品候補、在庫候補、案件、BOM行への接続

**共通UI方針:**
- 各ツールは `仕様・前提確認` → `パラメータ入力` → `結果確認` → `次アクション` の順で確認できる共通導線を持つ。これは説明文ではなく、画面上に常時見える作業フローとして出す。
- 各ツールの最上段に判定パネルを置き、計算表より先に `何が危ないか` と `次に触る条件` を見せる
- 入力フォームは `基本条件` `最悪条件` `部品定格` `出力/保存` の4群へ整理する
- 回路要素を扱うツールは `回路コンテキストパネル` を持ち、簡易回路図またはブロック図で入力欄の部品記号を説明する
- 有識者レビューでは、機能充足だけでなく、ユーザーの仕様・前提確認、パラメータ入力、結果確認、次アクションの導線と、画面上の仕様感を確認対象にする。指摘は実装・テスト・再レビューで0件になるまでPDCAを回す。

**2026-04-30 実用品質化: 危険なPASSを避ける追加基準**
- 電解コンデンサ寿命は、温度係数とリプル自己発熱で寿命を見積もり、電圧条件では寿命倍率を増やさない。電圧は定格超過とディレーティングで判定する。
- シャント電流検出は、ローサイド・シャント、ケルビン配線、電流検出アンプ、ADCの位置関係を図で示す。片方向のオフセットなし測定と双方向の0A出力オフセット測定を選択し、入力電流から `Vshunt -> Vout -> ADCコード`、最小/最大電流時のアンプ出力電圧、ADC入力範囲余裕、アンプ出力スイング余裕、ADCレンジ使用率を表示する。入力オフセットは `Vos / Rs` の入力換算誤差として扱い、損失は固定mW閾値ではなく測定レンジ最大電流と入力したRs電力定格に対する余裕でFAIL/WARNにする。ADC/アンプ電圧範囲が成立していてもRs定格超過なら、FAIL理由として定格超過を明示する。
- 電源余裕は、通常負荷合計と供給電力を直接比較して通常余裕を表示する。負荷ごとにレール名を指定でき、未指定時だけ電圧一致で自動割当する。効率は子レール負荷を親レールへ積み上げる上流換算にだけ使う。突入電流AはWへ換算せず、時間幅・対象レール・ピーク電流定格が未入力ならCHECK条件として残す。
- 比較器は、Vin入力先を `+入力(非反転)` / `-入力(反転)` で切り替え、基準方式はVref方式/Vcc分圧方式を選ぶ。正帰還は常にV+へ戻す。+入力方式と-入力Vref方式は従来通りR1を使い、Vin上昇時/下降時しきい値と出力遷移を分けて表示する。-入力+VCC分圧方式だけはR1をショート扱いにし、R2/R4をテブナン等価の基準電圧/Rthとして、R2||R4とR3でヒステリシス幅を算出する。
- 熱抵抗チェーンは `P発熱源 -> Rthチェーン -> Ta周囲温度` の向きで表示し、通常条件のTj超過だけをFAILとする。ワースト倍率超過やディレーティング不足はWARNに留め、通常条件が成立している設計をFAILにしない。
- I2Cは立上り時間だけでなく、プルアップ抵抗によるLowシンク電流も判定する。
- TVS、ヒューズ、ポリスイッチ、保護協調は、波形、時間電流特性、温度ディレーティング、動作順序が不足する場合、定格上の余裕があってもPASSではなくCHECKにする。異なる単位の余裕値を直接比較せず、素子ごとの余裕率と不足条件で判定する。
- 登録部品から解析入力へ取り込むスペック値は、`kΩ`、`uF`、`mV`、`nF`、`KiB` などの接頭辞を解釈し、単位事故を起こさない。
- EIA-96早見表は、チップ抵抗器の3文字マーキング専用として、2桁インデックス、倍率文字、抵抗値、逆引き候補、別表記R/S/Hを同じ画面で確認する。0Ω、3桁/4桁SMDコード、メーカー独自表記、マーキング省略品は不足条件として残す。
- `R1` `R2` `R3` `Rs` などのラベルは、図中記号、入力欄、式、判定文で同じ名前を使い、入力欄では必ず役割名を添える
- 入力欄のフォーカスまたは図中要素の選択で、対応する部品・信号・式の一部をハイライトする
- トポロジ選択があるツールでは、選択肢に応じて図、式、仮定条件を切り替える
- 条件不足時は計算欄を空にせず `CHECK` として不足条件を列挙する
- `PASS` でも「未評価条件」は必ず残す。例: 温度未評価、リプル未評価、突入未評価
- 判定根拠は文章だけでなく、marginカード、支配要因チップ、候補比較表で表示する

**保存・連携方針:**
- 解析結果は `analysis_sessions` としてDB保存する。APIは `/api/analysis-sessions` で、認証ユーザーが閲覧でき、作成・更新・削除は editor 以上が行う。
- 保存対象は `tool_id` `title` `verdict` `summary` `input_payload` `result_payload` `candidate_links` `project_id` `component_id` `bom_line_key` `created_by` `updated_by`。
- 設計解析画面の結果カードは `CHECK`、不足条件、前提、コピー用1段落サマリ、保存先の案件ID・部品ID・BOM行キーを持つ。
- 部品候補に接続するツールでは、入力欄へ部品DBのスペック値を取り込めるようにする。
- 在庫候補に接続するツールでは、候補が同等性能でも在庫・入手性で比較できるようにする。
- 案件保存では、後から「なぜこの部品/定数にしたか」を追える設計メモとして残す。
- 実装では、設計解析画面の共通出力/保存パネルに `案件検索(ProjectComboBox)`、`部品検索`、`部品から取り込み`、`保存済み解析一覧`、`差分表示`、`入力へ復元`、`削除`、`解析テンプレート` を置く。部品選択時は `/api/components/{id}` のスペック値を現在ツールの入力へ可能な範囲で反映し、結果カードの `candidate_links` には部品詳細、在庫数、部品候補検索へのリンクを含める。
- 保存済み解析一覧、入力復元、削除確認は共通保存パネルで実装済み。保存パネルはID直接入力を使わず、案件は案件名/事業名/案件番号検索、部品は型番/通称/メーカー検索で選択する。
- 解析テンプレートは初期状態として `MCU ADC入力`、`3.3V電源`、`I2Cバス`、`TVS保護` を持ち、入力へ反映するだけでなく、現在のユーザー・案件ID・部品ID・BOM行キー付きの `analysis_sessions` として複製保存できる。
- 保存済み解析との差分比較では、同一 `tool_id` と任意の `project_id` / `component_id` / `bom_line_key` で保存済み解析を取得し、現在入力との差分と前回/今回の verdict を表示する。
- 保存運用は「保存セッション一覧→入力へ復元→削除」で閉じる導線を、設計解析ツールハブの全ツールで共通実装する。共通保存API (`/api/analysis-sessions`) は実装済み（作成/更新/参照/削除）なので、UIで以下を揃える。
  - `保存セッション一覧`: `tool_id` は必須で絞り込み条件に必ず含め、必要時に `project_id` / `component_id` / `bom_line_key` で補助絞り込みする。表示は `updated_at` 降順、`title / verdict / summary / 案件 / 部品 / BOM行 / 作成日` を確認できること。
  - `保存セッション呼び出し`: 選択したセッションの `input_payload` を現在ツールの入力へ反映し、`outputSave` の紐づけ情報を上書きする。呼び出し後は差分比較（保存済み前回値 vs 現在入力）が見える状態を保持する。
  - `保存セッション削除`: `editor` 以上で確認導線（確認文＋対象名確認）を経て `DELETE /api/analysis-sessions/{id}` を実行し、成功時は一覧を更新して入力復元対象を明示解除する。削除時は差分表示をクリアする。
  - 保存一覧が空時、取得失敗時、権限不足時のメッセージはエラーメッセージで固定し、再試行導線を持つこと。
- 保存セッション導線の共通実装対象（SCR-016 設計解析ツールハブ: 実装済み）
  - ネットワーク探索 / 分圧 / 可変抵抗 / EIA-96早見表
  - ADCスケーリング / コンデンサ寿命 / NTC/PTC温度変換 / 電流検出 / 電源余裕 / バッテリー稼働 / 比較器 / 熱設計 / IF余裕
  - 誤差/歩留まり / 周波数応答 / 過電圧保護 / TVS保護 / ヒューズ選定 / ポリスイッチ / 保護協調
  - ロジックIC参照 / コネクタ設計/ピン配置 / ケーブル判定 / 0Ω/Jumper整理 / 起動診断
- 設計解析ツールの実装は、親 `design-tools.js` と親 `design-tools.blade.php` に全責務を集めない。機能別JSモジュールとBlade partialへ分割し、親はタブ/共通導線/呼び出しへ限定する。公開setup関数と主要ヘルパーは目的、入力、出力、副作用をコメントで明示し、各ファイルは1000行程度の目安を超えないように保守する。
- 2026-05-03 の全体対応として、上記基準を設計解析ツール周辺だけでなく一次コード全体へ拡大する。対象は `app/`、`routes/`、`database/`、`resources/js/`、`resources/views/`、`tests/`、`public/tampermonkey/` の自作コードとし、vendor、node_modules、build生成物、lock、画像/バイナリは除外する。部品登録/詳細、マスタ管理、エンジニア電卓、抵抗/容量探索、NetworkSearch、UiApiSurfaceSmoke、Tampermonkey補助は責務単位で分割し、公開関数、Controller/Request/Model/Service/Testの関数、主要ヘルパー、副作用を持つ操作関数へ、目的、機能、入力、出力、動作条件、副作用を明示する。

### SCR-001 部品一覧画面

**参照プロト：** `詳細仕様/UI構成/components_list.html`

**ユースケース定義（2026-04-10 再インタビュー反映）：**

SCR-001 は、異常部品の対処画面ではなく **既知部品や候補群を探索し、比較・詳細確認・編集へつなぐ探索画面** と定義する。  
在庫警告や発注判断のような「対処」は `SCR-012 在庫警告一覧` の責務とし、SCR-001 では在庫情報を判断材料として見せるに留める。

**主ユースケース（優先順）：**

1. `既知部品の直検索`
   - 型番、通称、メーカー名から目当ての部品を最短で開く
   - 到達先: SCR-002 部品詳細

2. `候補群の絞り込み探索`
   - 部品分類、入手可否、主要スペックから比較候補の母集団を作る
   - 到達先: SCR-004 部品比較

3. `代替候補の探索`
   - EOL、在庫不足、案件都合などで近い候補を探す
   - 到達先: SCR-002 / SCR-004

4. `登録内容の棚卸し`
   - 最近更新、情報不足、部品分類の偏りなどを見て編集対象を探す
   - 到達先: SCR-003 部品登録/編集

5. `一覧起点の次操作`
   - 詳細確認、比較、編集、新規登録へ迷わず遷移する

**責務外ユースケース：**
- 在庫警告部品だけを継続監視する
- 発注対象をまとめて洗い出す
- 在庫逼迫状態を一覧の主目的として扱う

これらは `SCR-012 在庫警告一覧` の責務とする。

**フィルター方針：**
- 常設するのは主ユースケース達成に直接効く条件に限る
  - キーワード
  - 部品分類
  - 入手可否
  - 並び順
- 詳細条件へ送るのは、候補探索や代替探索でのみ使う軸に限る
  - メーカー
  - パッケージ
  - スペック詳細 + 数値範囲
  - 在庫下限
- 在庫警告専用のフィルタは常設しない。必要なら SCR-012 へ遷移させる
- `在庫警告のみ` を部品一覧の主フィルタには置かない

**部品カード（1件）の構成：**
```
[thumbnail画像]  [部品情報]
                  list-title: 型番（→ SCR-002へのリンク。通称より優先）
                  list-value: 通称 / メーカー / 部品名
                  list-value: スペック概要（値+単位）
                  list-value: 商社名リンク + 価格
                  list-label/value: 新品 xxx個 / 中古 xxx個
                  list-value: データシートリンク（lucide file-downアイコン）※なければ非表示
                  list-value: パッケージ（lucide microchipアイコン）
```

**カード背景：** `card-even` / `card-odd` で交互塗り分け

**識別情報の優先順位：**
- 電子部品の一覧カードでは `型番` を主見出しにする。通称は検索補助・人間向けの別名として扱い、型番より大きく表示しない。
- 通称、部品名、メーカーは2行目の補足情報にまとめる。型番が未入力の場合のみ部品名を主見出しにフォールバックする。
- 候補比較や発注、データシート照合で使う識別子は型番であり、通称を主キーのように見せるUIにはしない。

**ページネーション：** 20件/ページ。ソート順はユーザーが設定可能。デフォルトは `部品分類 -> パッケージ分類 -> パッケージ -> 型番` の台帳順とし、最近触った部品を探す場合だけ `更新順` を明示選択する。型番順は単純な文字列順ではなく、型番内の数字を数値として扱う自然順にする。例: `2SC945` は `2SC1815` より前。

**アクション：**
- `+ 新規登録` ボタン → SCR-003へ遷移
- カード部品名クリック → SCR-002へ遷移
- カード複数選択チェックボックス → `比較する` ボタンが現れ SCR-004へ遷移

**設計メモ：**
- 2026-04-10 の `部品一覧ユースケース定義_再インタビュー` では、第一ユースケースは `直検索` `候補探索` `代替探索` に割れたが、4名とも SCR-001 の中核を `探索` と位置付けた
- 同再インタビューで、`在庫警告の監視` や `発注処理` は SCR-001 の責務外とされ、SCR-012 側へ分離すべきと一致した
- よって SCR-001 のUI検討は、見た目の好みではなく上記1〜5のユースケースを最短で回せるかを評価軸とする

### SCR-003 部品新規登録画面

**参照プロト：** `詳細仕様/UI構成/component_create.html`

**セクション構成（順番固定）：**

| # | セクション | 主な入力項目 |
|---|---|---|
| 1 | 基本情報 | 部品画像・データシート・部品名*・型番*・通称・メーカー*・代表保管棚 |
| 2 | 部品分類 / パッケージ | 部品分類*、パッケージ分類* + パッケージ詳細* |
| 3 | スペック情報 | 部品分類内のスペック詳細選択 → 値profile選択 → 値入力 → 単位選択（`+` で動的追加） |
| 4 | 在庫情報 | 新品在庫数 / 中古在庫数 |
| 5 | 価格情報 | 商社選択 + 価格（`+` で複数追加） |
| 6 | カスタムコード | 種別選択 + 値（`+` で動的追加） |

`*` は必須項目。

**スペック入力グリッド：** `grid-cols-spec`（スペック詳細 | profile | 値欄 | 単位 | 基底値プレビュー | 削除ボタン）の6列カスタムグリッド

**削除操作：** 確認モーダル表示（削除対象の内容を明示したメッセージ + キャンセル/削除ボタン）

**テーマ設定：** `localStorage` に保存し、ページ再読み込み時に復元

**運用補足：**
- 初期データ取得失敗時は、空画面のまま続行させず `再読込 / 戻る / マスタ管理` の復旧導線を出す
- マスタ管理のインライン編集も、保存ボタンがある画面では未保存差分を `dirty` として扱う。F5、ブラウザ戻る、画面内リンク、タブ切替、編集中対象の切替で変更が失われる場合は確認を出す
- `部品分類 / 商社` はコンボボックス型で候補絞り込みに対応する
- `パッケージ` は `パッケージ分類 -> パッケージ` の2段UIとする。1行目はドロップダウン、2行目はパッケージ分類で絞り込まれたスクロール付きフィルタコンボボックスとする
- `1部品 = 1パッケージ` を正式ルールとし、パッケージ違いは別部品として登録する。DIP/SOP のような派生は `部品複製` で入力コストを下げる
- `パッケージ分類` と `パッケージ` は `マスタ管理` で個別に保守する。パッケージは必ず親のパッケージ分類を持ち、並び順はパッケージ分類内で管理する
- `部品一覧` の詳細条件でも、パッケージ絞り込みは `パッケージ分類 -> パッケージ` の2段式で統一する
- スペック詳細は巨大な全件 `select` にしない。`部品分類 -> スペック詳細` の2段選択を基本とし、選択中部品分類の候補・共通スペック詳細・検索結果を最大件数つきで表示する
- 部品登録では `部品分類 / パッケージ` をスペックより先に配置する。スペック編集UI内では `部品分類` select でマスタ上の部品分類または `フィルタしない` を選び、暗黙の全件フォールバックや説明カード主体のUIにはしない
- 部品詳細のスペック編集では、上段を `部品分類` select、`スペック候補` dropdown + `追加`、`入力テンプレート` dropdown + `一式追加` で固定し、罫線下段に `スペックを新規で追加` を置く。下部に `登録済みスペック` を並べ、保存済み項目は候補外でも登録済み行から落とさない
- 選択した部品分類に紐づく入力テンプレートを提示する。例: `BJT` なら `BJT基本`、`MOSFET` なら `MOSFET基本`、`OPアンプ` なら `OPアンプ基本`、`マイコン` なら `マイコン基本`。テンプレート選択時は実際に追加されるスペック詳細をチップでプレビューする
- テンプレート適用は保存ではなく入力行生成であり、ユーザーは適用後に値・profile・単位を確認して保存する
- データシート解析ヘルパーは、抽出した部品種別から部品分類・候補スペック詳細・入力テンプレートを提示する。自動適用ではなくレビュー画面で選択させる
- 商社の新規追加は管理者のみ許可し、編集者には既存選択のみ見せる
- 長いフォームのため、保存導線は上部だけでなく下部アクション行にも置く
- 未保存変更がある間は `dirty` 判定で離脱確認を出す

#### SCR-003 拡張: PDFデータシート解析ヘルパー（ChatGPT Web 自動解析を主導線とする）

**目的：** データシートからの情報抽出は `ChatGPT 画面での手貼り` が最も面倒なので、普段の運用は `PDF選択 -> 解析開始 -> 結果レビュー -> 保存` の4ステップへ圧縮する。  
ただし電子部品データシートは誤抽出コストが高いので、**結果は必ずレビューしてから適用** し、自動入力だけで即保存はさせない。

**運用モード（優先順）：**
1. `Tampermonkey + ChatGPT Web 自動解析`
2. `ChatGPTから貼り付け` モーダル（自動化失敗時の fallback）
3. `Gemini 直結解析`（API 利用を許容する環境だけの任意モード）

**プロンプトの単一ソース：**
- ChatGPT へ渡す指示文は `/web/documents/BitsKeep/プロンプト/データシート解析プロンプト.md` を唯一の正本とする
- フロントや userscript に別の prompt 文字列をベタ書きしない
- サーバー側で上記ファイルを読み、`プロンプト本文（ここからコピー）` 以下を `prompt_text` として返却する

**UX設計方針：**
- 待ち時間が30秒以上になることを前提に、`待機UIはモーダルにしない`
- 解析中でも部品登録フォームの他項目は触れるようにする
- 自動解析が失敗しても、同じ画面のまま `貼り付け fallback` へ即切り替えられるようにする
- 複数PDFがある場合も、解析対象は1件だけ明示選択させて迷わせない

**データシート欄 UI 詳細：**

| 領域 | 役割 | UX上の意図 |
|---|---|---|
| PDFリスト | 選択済み PDF の一覧。各行に `解析対象` ラベルまたは `解析対象にする` 操作を置く | 複数添付時に、どのPDFを ChatGPT に送るかをユーザーが一目で判断できるようにする |
| アクションバー | 主ボタン `ChatGPTで解析`、副ボタン `ChatGPTから貼り付け`、任意ボタン `Geminiで解析` | 普段使いの主導線を左端に固定し、fallback は常に見える位置へ置く |
| 状態チップ | `Tampermonkey接続済み` `自動解析準備中` `ChatGPT待ち` `結果受信` | 「今どこで止まっているか」を短文で把握できるようにする |
| 解析ジョブカード | 4段ステップ `PDF準備` `ChatGPT起動` `解析待ち` `結果確認` を表示 | 進行状況が見えず再クリックを連打する事故を防ぐ |
| 解析結果レビュー | `helperResult` をレビュー用モーダルで表示し、内容修正・追加・削除を許可する | 候補が多い時も一覧性を保ち、未一致項目をその場で既存マスタへ紐付けられるようにする |

**ボタンの有効条件：**
- `ChatGPTで解析` は解析対象PDFが1件決まっている時だけ有効
- `ChatGPTで解析` は `window.__bitskeepTampermonkeyHelper` が検出できない場合、無効化せず案内モーダルを開く。ただし部品登録画面を開いただけでは未接続モーダルを自動表示しない。案内はユーザーが解析操作を押した時だけ出す
- `ChatGPTから貼り付け` は常時使える fallback とする
- `Geminiで解析` は Gemini 設定済みの場合のみ表示する。主ボタンにはしない

**Tampermonkey + ChatGPT Web 自動解析フロー：**
1. ユーザーが部品登録画面で PDF を選び、`ChatGPTで解析` を押す
2. フロントが解析対象PDFを `POST /api/component-helper/chatgpt-jobs` へ送信する
3. サーバーは PDF を `storage/app/private/component-helper-temp/{uuid}.pdf` へ一時保存し、`temp_upload_token` `signed_download_url` `prompt_text` `expires_at` `sha256` を返す
4. BitsKeep 側 userscript が `GM_setValue` で job を公開し、`GM_openInTab` で ChatGPT タブを新規作成または再利用する
5. ChatGPT 側 userscript が job を検知し、`signed_download_url` から PDF を `Blob/File` として取得する
6. ChatGPT 側 userscript が `prompt_text` を入力し、PDF を添付して送信する
7. 応答が安定したら ChatGPT 側 userscript が JSON 本文または code block 内 JSON を抽出し、`GM_setValue` で結果を返す
8. BitsKeep 側 userscript が結果を受信し、既存の `parseChatGPTResult()` 経路へ流し込んでレビューパネルを表示する
9. ユーザーがレビューで適用を確定した後、部品保存時に `temp_datasheet_tokens[]` を一緒に送る
10. サーバーが temp PDF を正式な datasheet 保存先へ移動し、`component_datasheets` へ確定登録する

**なぜ結果 JSON を ChatGPT タブからサーバーへ直接 POST しないか：**
- `chatgpt.com` 側からの認証付き POST は CSRF / セッション / CORS の扱いが増え、単独運用の割に面倒が増える
- 今回の最小工数案では、**サーバーは temp PDF の保管と最終保存だけ** を担当し、解析結果は BitsKeep タブでレビューしてから通常の保存処理へ乗せる
- これにより、失敗時も `手動貼り付け` と同じ UI へ即座に切り替えられる

**一時PDFの扱い：**
- temp PDF の有効期限は 2 時間
- `signed_download_url` は自己完結型トークンとし、ChatGPT タブから cookie 無しで取得できる形式にする
- temp PDF は `保存成功` 時に正式保存先へ移動し、`消費済み token` は再利用不可
- 使われなかった temp PDF は期限切れ cleanup で削除する
- ユーザーが PDF をフォームから外した場合、対応する `temp_upload_token` もフォーム状態から外す

**レビューと適用のルール：**
- 自動解析と手動貼り付けの結果は、どちらもレビュー用モーダルへ必ず表示する
- レビュー対象は `part_number` `manufacturer` `common_name` `description` `部品分類候補` `入力テンプレート候補` `パッケージ候補` `specs` とする
- レビュー中は `部品分類候補 / スペック候補` の追加・削除を許可する
- `部品分類候補` は複数候補を並べ、既存 `spec_groups` へその場で紐付けた上で主部品分類を選択できる。複合部品では追加部品分類も選べる
- `入力テンプレート候補` は、適用対象の部品分類候補から `spec_templates` を引いて提示する。テンプレート選択時はレビュー中のスペック候補へ行を追加し、フォームへ即保存しない
- `パッケージ候補` は複数候補を並べ、既存 `package_groups / packages` へその場で紐付けた上で **登録対象は1件だけ選択** できる
- `specs` は `spec_types` へその場で手動紐付けできる
- 適用時に紐付け未完了の候補はスキップし、トーストで件数を返す
- 適用後も保存前なら値を書き換えられる。自動解析結果をロックしない

**異常系と fallback：**

| ケース | 画面の挙動 | ユーザーの次操作 |
|---|---|---|
| Tampermonkey 未接続 | 案内モーダルを表示し、`手動貼り付けへ切り替える` を出す | 貼り付けモーダルへ遷移 |
| ChatGPT 未ログイン | 状態チップを `ChatGPTログイン待ち` に変更し、ChatGPT タブを前面化 | ログイン後に `再開` |
| ChatGPT DOM 変更で自動化失敗 | 状態カードに `自動取得失敗` を表示し、`貼り付け fallback` を最前面に出す | ChatGPT の結果を手動貼り付け |
| JSON 抽出失敗 | raw テキストの冒頭を表示し、`貼り付けモーダルへコピー` ボタンを出す | ユーザーが不要部分を消して貼り付け |
| temp PDF 期限切れ | 状態カードを `再アップロード必要` にする | `ChatGPTで解析` を再実行 |
| ユーザーが途中キャンセル | 解析ジョブをローカル終了し、temp PDF は期限切れ cleanup に任せる | 再実行または手動入力 |
| 解析結果が空 | `データシートから情報を抽出できませんでした` を表示 | 手動貼り付け or 手入力 |

**Tampermonkey userscript の責務分離：**
- BitsKeep origin script
  - `window.__bitskeepTampermonkeyHelper` を公開して接続確認に使う
  - job 作成後の `GM_setValue` / `GM_addValueChangeListener` を担当する
  - JSON 結果を既存 Vue ロジックへ渡す
- ChatGPT origin script
  - job 取得、PDF download、prompt 入力、送信、結果抽出を担当する
  - DOM 変更や未ログイン時は失敗理由を job status として返す
  - **応答待機のストール判定**: 停止ボタン残留 + 90秒変化なし + 300文字以上 → 完了扱い
    - 思考モデル（o1/o3 系）は1分超の思考フェーズ中に短いテキストしか表示されないため、30秒・文字数無制限の旧判定では思考完了前に打ち切られていた
    - 300文字未満の短い応答はストール判定せず3分タイムアウトまで待機する

**Gemini 直結モードの位置づけ：**
- 既存の `POST /api/component-helper/analyze-datasheet` は残す
- ただし UI の主導線にはせず、連携設定で API キーを持つ環境だけの任意モードとする
- 単独運用の通常導線はあくまで `ChatGPT Web 自動解析` とする

**Gemini が抽出する情報：**
- `part_number`（型番）
- `manufacturer`（メーカー名）
- `common_name`（部品種別の通称）
- `component_types[]`（部品種別 / 部品分類候補の配列）
- `package_names[]`（パッケージ候補の配列）
- `description`（部品説明）
- `specs`（スペックリスト）：絶対最大定格・電気的特性・動作条件の各行を `{ name, value, unit }` 形式で取得

**Gemini 解析の送信ルール：**
- フロントは PDF 送信時に必ず `FormData` を multipart のまま送る
- `JSON.stringify(FormData)` してはならない
- `Geminiで解析` ボタンで `PDF がない` エラーが出る場合は、まずフロントの送信形式を確認する

**spec_type マッチング：**
- 既存 `spec_types` と名称が一致するものは自動マッチング
- 一致しないものはユーザーが「新しいスペックとして追加」か「無視」を選択

**Gemini APIキー設定（優先順）：**
1. `app_settings.gemini.api_key`（連携設定UIで入力した値）
2. `.env` の `GEMINI_API_KEY`（フォールバック）

**追加ルート：**
- `POST /api/component-helper/chatgpt-jobs` — temp PDF 保存、prompt_text・signed URL・token 返却
- `DELETE /api/component-helper/chatgpt-jobs/{token}` — 未使用 temp PDF の早期破棄
- `POST /api/component-helper/analyze-datasheet` — Gemini 直結解析（任意モード）

**追加ルート（サーバ側非同期解析 / 2026-07-30 実装）：**
- `POST /api/datasheet-analyses` — 解析登録。`pdf` ファイルまたは既存 `temp_token` を受け、解析IDと初期状態を返す。結果は返さない

**追加 Web ルート：**

**追加設定ルート（連携設定ページに統合）：**

- `GET  /api/settings/integrations/datasheet-engine` — 解析方式の現在値、選択肢、方式ごとの利用可否と理由を返す

### FNC-004 profile対応スペック検索

FNC-003 の一部。`component_specs.value_profile / value_numeric_typ / value_numeric_min / value_numeric_max` を使用する。  
`typ` と `保証境界(min/max)` は意味が違うため、一律の `BETWEEN` や一律の `overlap` に潰さない。

**照合基準ごとの判定：**

| 照合基準 | 対象 profile | 判定 |
|---|---|---|
| `typ` | `typ`, `triple` | `value_numeric_typ BETWEEN query_min AND query_max` |
| `range` | `range`, `triple` | `value_numeric_max >= query_min AND value_numeric_min <= query_max` |
| `max` | `max_only`, `triple` | `value_numeric_max BETWEEN query_min AND query_max` |
| `min` | `min_only`, `triple` | `value_numeric_min BETWEEN query_min AND query_max` |

検索条件の `spec_min / spec_max / spec_unit` もサーバー側で基底単位へ正規化してから比較する。  
そのため、以下は同じ意味として扱う。

- `1` + `uA`
- `0.000001` + `A`
- `1e-6` + `A`
- `1uA` + 単位空欄
- `1u` + `A`
- `1KΩ` + 単位空欄
- `1kΩ` + 単位空欄
- `1000` + `Ω`

検索は単位文字列の一致ではなく、正規化後の `query_min/query_max + normalized_unit` で比較する。したがって `1KΩ` と `1kΩ` はどちらも `1000 Ω` として扱う。単位だけを指定して数値範囲を指定しない検索は補助的な文字列検索に留め、パラメータ検索の主経路は必ず数値正規化を通す。

`max_only` を `typ` 検索へ混ぜたり、`typ` を `max` 検索へ混ぜたりしない。  
意味の違う値を曖昧に合流させると、設計上の余裕判断を誤らせるためである。

**パラメータ検索UI方針（2軸構造）：**

```
[スペック詳細コンボボックス      ▼]  [TYP] [MAX] [MIN] [MIN..MAX] [MIN/TYP/MAX]
 テキスト入力で候補をリアルタイム絞り込み   ↑ profile選択（未選択=全profile）
 → 候補から1件確定選択（自由文字列ではない）
```

- スペック詳細はコンボボックス。入力中にリアルタイムで `name_ja / name_en / symbol / alias` を横断絞り込みし、最終的にドロップダウン選択で確定する（自由文字列のまま保存しない）
- profileはボタン選択。複数選択可。未選択時はprofile問わず全件を対象とする
- 2軸を独立操作することで「最大ベース電流で壊れないトランジスタを探す」（スペック詳細=ベース電流、profile=最大）と「typベース電流で互換品を探す」（スペック詳細=ベース電流、profile=typ）を自然に表現できる

### FNC-005 類似部品検索

**起点：** SCR-002 部品詳細画面の「類似部品を探す」ボタン

**ロジック：** 起点部品の以下の条件をパラメータとして SCR-001 に渡す
1. `category`（同じ部品分類）
2. 主要 `spec_type`（value / voltage / current / power）の `typ` 値 `value_numeric_typ` を起点に ±30% 範囲

`range / max_only / min_only` は類似度の代表値に使わない。  
理由は、保証境界や上限値を `typ` の代理にすると、実使用時の近さではなく「最悪条件の近さ」で候補が寄ってしまい、設計者の判断を誤らせるからである。

`triple` は `value_numeric_typ` を持つため、類似部品探索に利用できる。  
`typ` を持たない部品は、類似部品探索ボタンの表示条件から除外する。

**遷移先：** SCR-001（フィルター適用済み状態で表示）
**比較への導線：** SCR-001でヒット件数が複数の場合、チェックして SCR-004 へ進める

**「類似部品を探す」ボタン表示条件：** component_specs に主要スペックの `typ` または `triple.typ` が1件以上登録されている場合のみ表示

### FNC-016 案件参照管理

**画面：** SCR-005 案件管理画面

**案件ソース：**
- Notion 配下の `010_xxx`〜`099_xxx` 事業ページにある `01_案件管理`
- BitsKeep 独自案件

**運用ルール：**
- Notion由来案件はタイトル項目 `案件` を `projects.name` に同期する
- `案件番号` は `projects.external_code`、NotionページURLは `projects.external_url` に保持する
- 親ページ名 `010_`〜`099_` の数値プレフィックスを `business_code`、残りを `business_name` として保持する
- Notion由来案件は BitsKeep 上では参照専用。編集・削除はNotion側で行う
- 独自案件のみ作成・編集・削除を許可する
- 同名案件が複数ソースに存在しても統合しない。`source_type + source_key` を一意キーとして扱う
- `998_事業テンプレート` のような対象外ページは同期対象から除外する

**CRUD：**
- 作成：独自案件のみ。案件名・説明・所属事業を入力して登録
- 編集：独自案件の名称・説明の変更
- 削除：独自案件のみ論理削除（`deleted_at`）。紐づき部品（`component_project`）は保持
- 一覧：事業名・案件名・案件番号・起点・使用部品数・同期状態・最終同期日/最終更新日を表示
- 同期：対象事業配下の `01_案件管理` を自動発見し、案件一覧を再取得して `projects` に upsert
- 案件選択：全画面共通で `ProjectComboBox` を使用し、事業名・案件名でインクリメンタル絞り込みする

**案件同期UI方針：**
- 案件同期は説明文で使い方を教え込むのではなく、`未設定 / 要確認 / 未実行 / 実行中 / 0件 / 成功 / 失敗` の状態を先に表示する
- 各状態では `何が起きているか` と `次に押す操作` だけを短く示し、長文の手順説明は常設しない
- `未設定` は不足設定、`要確認` は接続/共有エラー、`0件` は対象発見または案件件数ゼロを区別して見せる
- 同期カードから `再同期` または `連携設定` へ直接遷移できることを優先し、説明テキストは補助に留める

**部品構成リスト（案件詳細）：**
紐づいている部品を一覧表示。商社選択プルダウンで「この商社で全部品を注文した場合の合計金額」を試算して表示する。

- `スペック詳細` タブは左ペインで `部品分類` を選び、右ペインで「左で選んだ部品分類に持たせるスペック詳細を追加・編集・アーカイブする」画面として見せる。画面説明に `主所属` や `全件一覧` のような内部都合の言葉は出さない。実装上は選択中部品分類を `owner_spec_group_id` に持つ `spec_scope='group_local'` かつ `spec_kind='normal'` のスペック詳細だけを扱う。候補内での扱いは編集しない
- `スペック候補設定` タブは、左ペインで `部品分類` を選び、右ペインで部品分類内の `候補スペック詳細` の採用可否・並び順・必須/推奨・既定profile・既定単位・メモを編集する。候補追加、候補設定編集、候補行のドラッグ&ドロップ並び替えは操作完了時に自動保存し、上下ボタンは置かない。候補一覧上の扱い・既定・メモは読み取り表示とし、行の `編集` から候補設定専用モーダルを開く
- `スペック候補設定` の `編集` は `spec_group_spec_type` 側の範囲・扱い・既定profile・既定単位・メモだけを扱う。名称・記号・alias・単位などスペック詳細そのものの編集は `スペック詳細` / `共通スペック詳細` / `許容差スペック詳細` 側の `編集` で行う
- `スペック候補設定` で候補を追加する操作は `スペック詳細から追加`、`共通スペック詳細から追加`、`許容差スペック詳細から追加` の3ボタンに分ける。ここでは既存スペック詳細から選ぶだけで、スペック詳細のフリー入力・新規作成モーダルは開かない
- 部品分類ごとのスペック詳細、共通スペック詳細、許容差スペック詳細そのものへの操作は `追加 / 編集 / アーカイブ / 復元` に統一する。部品分類内の候補関係は `候補に入れる / 候補から外す` と表示し、`削除` と混同させない。`候補から外す` だけは確認ダイアログを挟む。`候補に入れる` / `候補から外す` のボタンは固定幅にし、文字数差で表崩れを起こさない
- `入力テンプレート` タブは、左ペインで `部品分類` を選び、テンプレートとテンプレート行の既定profile・既定単位・必須/任意を編集する。テンプレート編集モーダルは行内のスペック詳細名が読める幅を確保し、テンプレート行のスペック詳細候補は関連する部品分類の候補スペック詳細だけに絞る。既存テンプレートに候補外の行がある場合は、その行の現在選択値だけを `候補外` と分かる形で残し、保存時に誤って消えないようにする。タブ位置はスペック系タブの一番右に固定する
- マスタ管理内の追加・編集・候補選択系モーダルは内容量に合わせて幅を分ける。候補追加や入力テンプレート編集など一覧・行編集が必要なものは `modal-master`、パッケージ詳細とスペック詳細・共通スペック詳細・許容差スペック詳細の追加/編集は `modal-lg`、パッケージ分類・部品分類・候補設定編集は `modal-md` にする。短文の確認ダイアログだけは `modal-sm` のまま扱い、編集作業用モーダルと混ぜない
- マスタ管理の編集モーダルに `sort_order` の数値入力は出さない。`sort_order` は内部保存値であり、パッケージ分類、パッケージ詳細、部品分類、候補スペック詳細の並び替えは一覧上のドラッグ&ドロップで行う。ユーザーに `10 / 20 / 30` のような重み値を設計・入力させない
- `部品シリーズ` は、同一シリーズ内の値展開と値候補の部品化を扱う。E系列に乗る部品だけでなく、E12中心にE24値が混ざる運用、ツェナー電圧・水晶周波数・ヒューズ電流・コネクタ極数の任意値展開も正式に扱う
- `共通スペック詳細` タブは左ペインで `部品分類` を選び、右ペインでは登録済みの共通スペック詳細から、選択中部品分類の入力候補に入れるものを選ばせる。内部的には `spec_scope='common'` かつ `spec_kind='normal'` の一覧・追加・編集・アーカイブ・復元と、選択中部品分類への `候補に入れる / 候補から外す` を扱う
- `許容差スペック詳細` タブも左ペインで `部品分類` を選び、右ペインでは登録済みの許容差スペック詳細から、選択中部品分類の入力候補に入れるものを選ばせる。内部的には `spec_kind='tolerance'` の一覧・追加・編集・アーカイブ・復元と、選択中部品分類への `候補に入れる / 候補から外す` を扱う。通常/許容差を切り替えるラジオボタンは置かない。許容差スペック詳細タブ内では全行が許容差なので、行内の `許容差` バッジは置かない
- `共通` はユーザーが選択する `部品分類` としては持たない。既存DBに `spec_groups.name='共通'` がある場合は、共通スペック詳細へ移行して `spec_groups` から削除する
- `入力テンプレート` は `入力テンプレート` タブ内の選択中部品分類に紐づけ、テンプレート内の行順、既定profile、既定単位、必須/任意を管理できるようにする。テンプレート行へ登録できるスペック詳細は、その部品分類の `spec_group_spec_type` 候補を基本とする
- タブ状態は URL の `tab` クエリで保持する。`/master?tab=packages` のような URL で直接開け、リロードとブラウザ戻る/進むでも選択タブを復元する

**用語差分と設計負債：**
- UI表示名は `部品分類` / `パッケージ詳細` / `スペック詳細` / `スペック候補設定` / `候補スペック詳細` / `入力テンプレート` / `共通スペック詳細` / `許容差スペック詳細` に整理した。
- DB/API/コード内部名は、互換性と改修範囲を抑えるため現行名を正式名として維持する。現時点では内部改名を行わない。

### FNC-022 受動部品ネットワーク/分圧設計（設計解析ツール）

**起点：** SCR-016 設計解析ツールハブ配下の受動部品ネットワーク/分圧設計。設計解析ツール内では `ネットワーク探索` / `分圧` / `可変抵抗` をメインタブとして扱い、R/C探索、通常分圧、VR分圧、可変抵抗を同じ操作面で扱う。

**位置付け：**
- 抵抗/容量ネットワーク探索は設計解析ツール群の1機能であり、独立カテゴリの別製品として扱わない
- これまで別扱いに見えた理由は、探索APIと高密度な専用画面を先に実装したためであり、UX上の正しい分類ではない
- 通常分圧とVR分圧の正本は本機能の `分圧` メインタブに置く
- 設計解析ツールハブの `NTC/PTC温度変換` は、NTC/PTC温度モデル、温度-電圧グラフ、感度の良い/悪い温度域、測定対象温度範囲の感度、サーミスタ電力損失、自己発熱、抵抗公差/サーミスタ公差の電圧破線、ADCコード表、線形化、固定抵抗候補に責務を絞る。通常分圧/VR分圧の電気的な候補選定、負荷計算、素子許容差範囲は本機能の分圧エンジンを共通利用する

**対象：**
- 抵抗
- コンデンサ
- 分圧回路

**機能：**
- 目標値と許容誤差を入力
- 既存の `tolerance_pct` は、目標値または理想値に対して候補を採用するための探索許容誤差として維持する
- `部品許容差`（`element_tolerance_pct`）を別概念として追加する。抵抗/容量ネットワーク候補では、選択された各公称部品のばらつき確認用として扱う
- 上位タブは `ネットワーク探索` / `分圧` / `可変抵抗` とする
- `ネットワーク探索` タブでは部品種別を選択（抵抗 / 容量）し、分圧UIは置かない
- `分圧` タブでは `VR調整なし` / `VR調整あり` のサブモードを選択する。両サブモードは同じ分圧設計条件を共有し、差分はVR素子を入れて出力範囲を調整するかどうかだけとする
- 候補集合は E系列（E6 / E12 / E24 / E48 / E96）、個別候補セット、在庫部品の抵抗値/容量値から選択する。部品シリーズの値展開ポリシー連携は次段階で扱う
- 探索対象を手持ち在庫（`inventory_blocks.quantity > 0`）限定に切り替え可能
- 素子数の最小/最大を指定可能
- ネットワーク種別を選択可能。現実装は最大4素子、返却上限80件、探索量上限あり
  - 直列
  - 並列
  - 直並列混在
  - 複数分岐を含む複雑ネットワーク
- `VR調整なし` では2抵抗の比率、総抵抗範囲、R1/R2の候補を探索する
- 分圧条件は目標比率指定に加え、Vin/Vout直接入力を持つ。Vin と Vout が指定された場合は `target_ratio = Vout / Vin` を計算し、その比率を探索条件へ使う。`VR調整あり` では同じ入力モードを使い、出力下限/上限を電圧または比率範囲として指定できる
- `VR調整なし` と `VR調整あり` は同じ負荷条件を持つ。抵抗負荷は出力ノードからGNDへの抵抗で、`∞` は無負荷とする。電流負荷は出力ノードから引き抜く電流で、`0A` は無負荷とする
- 無負荷の指定はタイピング必須にしない。抵抗負荷は `∞` ボタン、電流負荷は `0A` ボタンで無負荷へ戻せるUIにし、この操作を `VR調整なし` と `VR調整あり` の両方に用意する
- `VR調整あり` は `Vin -> R上 -> VR -> R下 -> GND` の直列列からVRワイパを出力するモデルとし、Vin、出力下限、出力上限、指定した基準VR値から R上/R下 の固定抵抗候補を出す。候補値ソース、許容誤差、総抵抗範囲、負荷条件は `VR調整なし` と同じ入力を使う
- `VR調整あり` の基準VR値は候補選定の緩い優先条件ではなく、設計で使うVR素子の公称値として固定する。たとえば `10kΩ` を指定した場合、探索は `10kΩ` のVRを前提に上側/下側固定抵抗を選び、`200Ω` のような大きく異なるVR値を採用候補にしない
- `VR調整なし` は候補ごとに分圧列の回路電流、負荷電流、R1/R2の消費電力、抵抗合計電力、負荷を含む総消費電力を表示する。これらは Vin が入力されている場合に算出する
- `VR調整あり` はワイパ端点で電流と電力が変わるため、端点評価から最大回路電流、R上/VR/R下の最大消費電力、抵抗合計最大電力を表示する
- `VR調整なし` は R1/R2 の許容差を個別入力でき、候補ごとに負荷込み出力比/出力電圧の独立RSS目安範囲と全素子コーナー範囲を表示する
- `VR調整あり` は R上/VR/R下 の許容差を個別入力でき、下限端/上限端の出力電圧について独立RSS目安範囲と全素子コーナー範囲を表示する
- 可変抵抗 + 固定抵抗設計では、算術上の `理想値` と、実際に採用できる `採用候補` を別枠で表示する
- 可変抵抗設計の採用候補は、現実装では固定抵抗のE系列値、可変抵抗の標準VR値、ユーザー入力のカスタム値に限定する。`8kΩ` のような算術理想値を、そのまま固定抵抗の採用結果として扱わない
- 在庫値・登録部品・購入リンクは将来拡張または既存ネットワーク探索とは別扱いとする。現段階では、結果を購入可能・在庫採用品とは表現しない
- 計算結果は誤差昇順で上位候補を複数表示
- 各候補に回路表現、素子構成、公称値、誤差%、使用部品数、在庫由来かを表示
- 抵抗/容量ネットワーク候補には、公称合成値、独立ばらつきのRSS目安範囲、保証確認用の全素子同方向コーナー範囲、目標値または理想値からの最大絶対偏差/最大偏差%を表示する
- 結果の部品は SCR-002 へのリンク付き

**可変抵抗 + 固定抵抗設計の出力・判定：**
- 入力は `基準抵抗値` + `可変幅` から要求範囲を作る。可変幅は `%` と `Ω` の両方を受け付け、`%` は基準抵抗値に対する幅として扱う
- 基準位置は `上限基準` / `中心基準` / `下限基準` を持つ。既存互換は `上限基準` とし、`基準抵抗値=10kΩ`、`可変幅=20%` は `8kΩ〜10kΩ` の要求範囲になる
- 入力は上記要求範囲に加え、回路方式（直列/並列）、候補供給元（E系列、標準VR値、カスタム値）を持つ
- 理想値は設計参考として常に表示してよいが、採用候補一覧には供給元が明確な値だけを載せる
- 採用候補ごとに、固定抵抗値、可変抵抗値、供給元、端点結果、目標下限との差、目標上限との差、固定抵抗/VRの補正有無、可変抵抗の標準値、判定を表示する
- 固定抵抗とVRの許容差を個別入力でき、採用候補ごとに要求下限/上限端の独立RSS目安範囲と全素子コーナー範囲を表示する
- 固定抵抗の標準値化で要求範囲を満たせない場合は、VRを範囲側に補正し、固定抵抗を再計算する
- 直列はVR値を要求幅以上に上げる。並列は低端側を満たせるVRと固定抵抗を再計算する
- 判定は `CHECK` / `WARN` とする。現実装では在庫・登録部品・購入リンクが未連携のため `PASS` は出さない。端点が要求範囲を包含する標準値候補は `CHECK`、要求範囲を満たせない候補は `WARN` とする
- 固定抵抗/VRの補正有無は、理想値近傍か、範囲確保のため再計算した値かをタグで表示する。可変抵抗は、採用VR値が標準VR値・カスタム値のどれかを明示する
- 現段階の実装はフロント計算でよい。既存の抵抗/容量ネットワーク探索APIと在庫限定探索は別経路でもよいが、UI上は在庫由来でない候補を購入可能とは扱わない

**分圧の負荷モデル：**
- `VR調整なし` は `Vin -> R1 -> Vout -> R2 -> GND` とする。抵抗負荷は R2 と並列に入る出力-GND負荷として扱い、`∞` は並列負荷なしにする
- 電流負荷は Vout ノードからGNDへ引き抜く定電流として扱う。候補評価では `Vin`、上側抵抗、下側抵抗、負荷電流から負荷込み Vout を計算し、`0A` は無負荷にする。負荷電流が大きく成立しない候補は `WARN` にする
- `VR調整あり` はワイパ下端側を出力下限、ワイパ上端側を出力上限として端点評価する。下限端点は `R上 + VR` を上側、`R下` を下側とし、上限端点は `R上` を上側、`VR + R下` を下側として扱う
- `VR調整あり` にも `VR調整なし` と同じ抵抗負荷/電流負荷を適用し、端点ごとに負荷込み Vout、目標下限/上限との差、CHECK/WARN判定を表示する
- 回路電流は電源から上側抵抗列へ流れる電流として扱う。抵抗電力は各抵抗両端の電圧または枝電流から `P = I^2R = V^2/R` で算出し、VR調整ありでは端点の最大値を定格確認用に表示する
- 分圧の素子許容差範囲は、R1/R2またはR上/VR/R下の個別許容差から、独立RSS目安とコーナー範囲を分けて表示する。RSS目安は保証値ではなく、コーナー範囲は起きやすさを示すものではない
- 現実装は公称値・無負荷/指定負荷モデルであり、抵抗許容差、温度係数、VRワイパ抵抗、接触抵抗、電力、負荷の動的変動は別途確認項目として残す。このため分圧候補は `PASS` を出さず、条件が範囲を含む場合も `CHECK`、不足または成立しない場合は `WARN` とする

**計算ロジック：**
- `ネットワーク探索` タブの抵抗/容量ネットワーク探索はバックエンド（PHP）で実施する。可変抵抗 + 固定抵抗設計は現段階ではフロント計算で扱ってよい
- 探索空間が爆発しやすいため、素子数上限・候補集合・許容誤差で枝刈りする
- 出力は `text` / `json` 相当の内部表現を持ち、UIでは回路表現文字列と簡易図を表示する
- 抵抗とコンデンサは直列/並列の合成式が逆になるため、部品種別ごとに式を切り替える
- 部品許容差の主表示は独立ばらつきのRSS目安とする。各素子の正規化感度 `S_i = (∂f/∂x_i) * (x_i / f)` を数値微分で求め、合成値まわりの幅を `f * (element_tolerance_pct / 100) * sqrt(sum(S_i^2))` として表示する
- 対応する直列・並列・直並列混在のR/Cネットワーク式は各素子値に対して単調であるため、保証確認用のコーナー下限は全素子を `nominal * (1 - element_tolerance_pct / 100)`、上限は全素子を `nominal * (1 + element_tolerance_pct / 100)` として同じトポロジを評価して求める
- RSS目安は独立ばらつきの設計目安であり保証値ではない。全素子同方向コーナーは保証境界確認用で、起きやすさや確率を示すものではない。温度係数、電圧係数、経年変化、寄生成分、同一ロット相関、実測分布、モンテカルロ統計は扱わない
- 在庫限定探索では、部品に複数の数値スペックがある場合、抵抗値/容量値の単位・名称に合うスペックを優先し、定格電圧や許容差を値候補として使わない
- 分圧タブの `分圧` サブモードは `0 < target_ratio < 1`、`min_elements <= max_elements`、`total_res_min <= total_res_max` を成立条件にする。Vin/Vout直接入力では `Vin > 0`、`0 < Vout < Vin` を基本条件とし、電流負荷指定時は Vin 不足を入力エラーにする
- API応答は `summary`、`warnings`、`next_actions`、候補プール数、打ち切り有無、候補一覧を返し、UIは `result.candidates` を正として扱う
- 1〜2素子探索と分圧はE系列全体を使い、近い値探索の前処理で厳密解を落とさない。3素子以上の直並列混在は候補プールと探索量上限で打ち切り、UIに `evaluation_limited` と次アクションを出す

**参考機能レベル：**
- `shapoco/rc-combinator` 相当の複数素子ネットワーク探索と分圧探索を最終目標とする。現実装は最大4素子、分圧は2抵抗、部品シリーズ連携なしの段階。

### FNC-032b バッテリー稼働時間解析（付加機能）

**起点：** SCR-016 設計解析ツールハブ

**用途：** 周期的にON/OFFする負荷を電圧・電流・効率・ON時間で電力積算し、Wh/周期、平均電力、稼働時間、放電中の端子電圧を見積もる

**機能：**
- 入力UIは `電池パック`、`動作条件`、`周期負荷`、`結果` の順に分ける。`電池パック` は電池種類（LiPo、ニッケル水素、アルカリ、マンガン、鉛）、セル数、容量(Ah)、公称電圧、内部抵抗、使用可能容量%を入力する
- `動作条件` は周期時間、システム最低電圧、要求稼働時間を入力する
- 電池種類とセル数から一般的な満充電電圧、公称電圧、下限電圧を表示し、電池種類の変更時は一般的な電圧へ初期更新する
- `周期負荷` は負荷1セットを横並び、セットを縦並びにし、負荷ごとに名称、負荷電圧(V)、負荷電流(A)、変換効率(%)、ON時間(s)を入力する。`Wh/cycle = Σ((Vload * Iload / efficiency) * on_sec / 3600)` から平均電力とバッテリー平均電流を算出する。LED、CPU、GPSのような同時ON負荷を表現できるよう、ON秒数合計が周期時間を超えてもそれだけではFAILにしない。単一負荷のON時間が周期時間を超える場合は入力矛盾としてFAILにする
- `結果` は実効稼働時間と制限要因を主表示し、Wh/周期、平均電力、平均電流、全負荷同時ON前提のピーク負荷、容量ベース時間、電圧下限到達時間、グラフを表示する。容量100%消費時間は通常表示から外す。`capacity_runtime[h] = usable_energy[Wh] / average_power[W]`、`voltage_limit_runtime[h] = full_capacity_runtime[h] * discharge_depth_at(Vbat(load)=Vmin)`、`runtime[h] = min(capacity_runtime, voltage_limit_runtime)` を表示し、24h超は日、30日超は月、365日超は年スケールも追加表示する。内部抵抗による電圧降下は同時ONピーク負荷を使い、グラフ右端を負荷時電圧とシステム最低電圧の交点へ固定する。電圧降下グラフの右側には、周期負荷Whの合計を100%へ正規化した容量消費内訳円グラフを表示し、電池100%を使い切るまで各負荷が容量消費の何%を占めるかを出す
- 電池種類ごとの簡易セル放電曲線をセル数へスケールし、内部抵抗による電圧降下を加味した電圧-時間グラフを表示する。システム最低電圧が標準下限より低い場合は終端曲線を外挿して電圧下限到達時間へ反映し、深放電目安としてWARNする。横軸時間、縦軸電圧、最大時間ラベル、カーソルtooltipはプロット位置と一致させる。グラフ右端は負荷時バッテリー電圧がシステム最低電圧へ到達する交点とし、その時点を残量0%として扱う。グラフカード右上にはtooltipと同じ数値を重複表示しない
- グラフ上のマウス位置で時間、電圧、残容量%を表示
- ON秒数が周期を超える、容量/周期/平均電流が不正、開始時点で最低電圧を下回る場合はFAIL。温度、劣化、実測電流、レギュレータ効率、電池データシート曲線はCHECK条件に残す

- ユーザーテンプレート: 型番、メーカー、実装形態、定格電圧、定格電流、温度範囲、相手側型番、写真URL、図URL、データシートURL
- ピンマップ: ピン番号、表示位置、初期信号名、電源/信号/差動/シールド種別、標準電圧、標準電流、ペア/グループ
- ピン割付: 案件または部品ごとの信号名、電圧、電流、ケーブル色、AWG、注記、未接続理由
- 設計メモ: BOM注記、シルク注記、量産確認項目、定格根拠、視点図の不足条件

**UX構成：**
- 左ペイン: コネクタカタログ検索、規格/極数/ピッチ/実装形態/定格で絞り込み、ユーザー登録ボタン
- 中央: 写真/図つきピンマップ。嵌合面、はんだ面、ケーブル側を切り替え、Pin1、キー位置、視点反転を明示する
- 右ペイン: 選択ピンの信号名、電圧、電流、方向、ケーブル色、AWG、注記、並列グループ、差動ペア、定格marginを編集する
- 下段: ピン割付表、電源/信号/未割付サマリ、BOM注記、シルク注記、量産確認リストを表示する
- モードは `参照`、`ピン割付`、`電圧/電流確認`、`ケーブル/ハーネス`、`BOM/組立注記` に分ける

**判定・出力：**
- ピン別電流が定格とderating後定格を超える場合は `FAIL`
- 定格根拠、視点図、Pin1根拠、相手側部品、未割付ピン、NC理由が不足する場合は `PASS` にせず `CHECK`
- 電源ピンを並列使用する場合は、接触抵抗差、ホットプラグ順序、GND先行、シールド接続、逆挿し防止を確認項目として残す
- USB Type-C のCC/SBU、D-subのシェル、RJ45のペア割付、差動ペアの極性はテンプレート固有チェックを持つ
- 出力はピン配置表、図面注記、BOM注記、ハーネス表、未確認条件、次アクションを返す

**非目標：**
- 全メーカー型番の完全カタログ化は初期スコープ外
- データシート値の自動抽出は初期スコープ外。現実装は標準テンプレートとユーザー登録を正とし、根拠URL/画像を保存する

### FNC-024 Notion案件同期

**用途：** Notion 上の事業ページ群から対象案件DBを自動発見し、BitsKeep の `projects` テーブルへ同期して案件選択UIで統合的に扱えるようにする

**同期元：**
- DB名が `01_案件管理`
- 親ページ名が `010_`〜`099_` に一致する事業
- 例: `010_綾電クリエイト / 01_案件管理`
- 例: `011_eleXlink / 01_案件管理`
- 除外例: `998_事業テンプレート / 01_案件管理`

**取得対象項目：**
- `案件` → `projects.name`
- `案件番号` → `projects.external_code`
- 親ページ名 → `projects.business_code`, `projects.business_name`
- `顧客` / `納期` / `登録` → 一覧表示や将来検索用の補助情報として保持
- 対象DB/DataSource ID → `projects.source_database_key`
- Notion page URL / page ID → `projects.source_key`, `projects.external_url`

**発見ロジック：**
1. Notion 検索で `01_案件管理` を検索
2. database のみ抽出
3. ancestor/parent page 名が `^0[1-9][0-9]_.+` に一致するものだけ採用
4. `business_code` / `business_name` を親ページ名から分解
5. 各DBの案件行を取得して upsert

**同期方式：**
- SCR-005 の「Notion同期」ボタンから手動実行可能
- 案件選択コンボボックス表示時、前回同期から15分以上経過していれば自動再同期
- 同期は upsert。Notion側で名称変更された場合は `projects.name` を更新する
- Notion側でアーカイブされた案件は `deleted_at` をセットせず、`sync_state='archived'` 相当で選択不可にする
- 同期失敗した事業DBは `sync_state='error'` とし、他事業の同期は継続する

**実装優先度：** 高（案件選択機能の前提）

- 現時点では方向修正の記録として残し、実装進捗チェックリストの書き換えはまだ行わない

### ⑪ 詳細ドラフト: 起動・停止 / リセット / 依存関係診断

**参照プロト：**
- `詳細仕様/UI構成/startup_sequence_diag.html`

**位置づけ：**
- `⑨ 斬新候補` および `⑩ 反証許可付き再評価` で最も強く押し上げられた候補
- 詳細ドラフト先行で具体化し、テンプレート限定の初版実装対象として扱う
- 実装進捗チェックリストへ反映する

**目的：**
- 複数電源、EN/RESET、PG、クロック、ブート条件、外部機器、バックパワー経路の依存関係をまとめて扱い、`本当に立ち上がるか` `安全に停止できるか` を判定する
- 電源タイミングを 1 本計算するのではなく、`安全な順序` `禁止順序` `危険な時間窓` `最小修正案` を返す

**想定する症状起点：**
- `起動しない`
- `再起動だけ失敗する`
- `電源OFF中に逆給電する`
- `停止時にハングする`

**入力項目：**

| 区分 | 項目 | 内容 |
|---|---|---|
| シナリオ | `scenario_type` | `cold_start` `warm_reset` `power_down` `hot_plug` `partial_power` |
| 電源レール | `rail_id` `label` | 例: `vin`, `3v3_main`, `1v0_core`, `2v5_io` |
| 電源レール | `start_delay_ms` `rise_time_ms` `fall_time_ms` | 立上り/立下りの相対時間 |
| 電源レール | `valid_min_v` `valid_max_v` | レールが `有効` と見なせる範囲 |
| 電源レール | `pg_assert_v` `pg_delay_ms` | Power Good の成立条件 |
| 制御信号 | `signal_id` `signal_type` | `EN` `RESET` `PG` `CLK_OK` `BOOT_OK` `DONE` など |
| 制御信号 | `source_node` `target_node` | どこがどこを制御するか |
| 制御信号 | `active_level` `release_delay_ms` | 極性と解放遅延 |
| ブロック | `block_id` `block_type` | `PMIC` `REGULATOR` `MCU` `FPGA` `ADC` `SENSOR` `EXT_DEVICE` |
| ブロック | `required_rails` `required_signals` | 成立に必要なレール/信号 |
| ブロック | `min_hold_ms` | リセット保持や電源安定待ちの最小時間 |
| 依存関係 | `from_node` `to_node` `condition_type` | `rail_valid` `pg_high` `reset_release` `clock_stable` `boot_media_ready` |
| バックパワー | `path_id` `from_domain` `to_domain` | 逆給電経路 |
| バックパワー | `via_type` | `ESD_DIODE` `PULLUP` `LEVEL_SHIFTER` `IO_BUFFER` `PROTECTION_PATH` |
| バックパワー | `series_resistance` `isolation_component` | 抑制手段の有無 |
| 外部条件 | `external_device_state` | 相手機器の電源状態、接続状態 |

**内部モデル：**
- ノード種別は `Rail` `Signal` `Block` の 3 種類とする
- 依存関係は有向グラフで表現し、各ノードは時間軸上で `off` `ramping` `valid` `released` `invalid` の状態を取る
- `Rail` は電圧レンジと PG 条件を持つ
- `Signal` は極性、源、伝播遅延、対象ノードを持つ
- `Block` は必要レール、必要信号、最小保持時間、禁止状態を持つ
- `BackpowerPath` は OFF ドメインへ流れ込む逆給電経路として別テーブルで評価する
- 評価器はシナリオごとに時系列シミュレーションし、成立順序と禁止順序を判定する

**判定ルール：**
1. `Block` は、必要な `Rail` がすべて `valid` かつ必要な `Signal` が成立するまで `RESET_RELEASED` にしてはならない
2. `PG` や `EN` が循環依存を作る場合は `起動デッドロック` と判定する
3. 対象ドメインが `off` のまま入力信号だけ High になる経路がある場合は `バックパワーリスク` と判定する
4. `Rail` が `falling` に入った後も外部 I/O や pull-up で給電される場合は `部分給電リスク` と判定する
5. `min_hold_ms` を満たさずに `RESET` が解放される場合は `再起動不安定` と判定する
6. 必要な `CLK_OK` `BOOT_OK` が未成立のまま起動順序が進む場合は `初期化順違反` と判定する
7. 条件不足で順序を確定できない場合は `判定保留` を返し、不足入力を列挙する

**出力：**
- 総合判定: `成立` `要注意` `不成立` `判定保留`
- `safe_start_sequence`: 安全な起動順序
- `safe_stop_sequence`: 安全な停止順序
- `forbidden_sequences`: 禁止順序一覧
- `danger_windows`: 危険な時間窓と理由
- `backpower_paths`: 検出した逆給電経路
- `first_suspects`: 最初に疑うべきレール/信号/依存関係
- `minimal_fixes`: 例 `RESETを120ms遅らせる` `series抵抗を追加` `EN条件をPG依存へ変更`
- `timeline_view_model`: UI でタイムライン描画するための正規化済みデータ

**暫定API案：**

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/calc/startup-sequence/evaluate` | 起動/停止/依存関係診断を実行 |
| POST | `/calc/startup-sequence/templates` | よくある構成（PMIC+MCU, FPGA+DDR など）の雛形を生成 |

**暫定レスポンス例：**
```json
{
  "status": "warn",
  "safe_start_sequence": ["vin", "3v3_main", "1v0_core", "reset_mcu_release"],
  "forbidden_sequences": [
    {
      "sequence": ["usb_5v_alive", "mcu_io_high", "3v3_main_off"],
      "reason": "backpower_risk"
    }
  ],
  "minimal_fixes": [
    "mcu_reset_release を 80ms 遅らせる",
    "usb_uart_rx に series_resistance 1k を追加する"
  ],
  "missing_inputs": []
}
```

**UI方針：**
- 入口は `ツール名` ではなく `症状` から入る
- 上段に `成立 / 要注意 / 不成立` と `次に直す1項目` を固定表示する
- 中央は `依存関係グラフ` と `起動タイムライン` を並べ、どこで詰まっているかを視覚的に示す
- 下段に `危険な時間窓` `バックパワー経路` `最小修正案` を並べる
- `綺麗な解析図` より `最初に疑うべき場所` を優先表示する

### ⑭ 詳細ドラフト: 熱設計 / 熱抵抗チェーン可視化

**参照プロト：**
- `詳細仕様/UI構成/thermal_chain_diag.html`

**位置づけ：**
- 既存の `熱見積もり / 温度上昇推定` 候補を、`抵抗 / Reg / Tr` 向けの実務ツールとして具体化したもの
- 詳細ドラフト先行で具体化し、代表パッケージ限定の初版実装対象として扱う
- 実装進捗チェックリストへ反映する

**目的：**
- 部品ごとの損失から `どこで何℃上がっているか` を熱抵抗チェーン単位で可視化する
- `Tj` だけを返すのではなく、`P発熱源 -> junction -> case/tab/body -> TIM -> sink/pattern -> Ta周囲温度` の各段を積み上げて見せる
- 抵抗、レギュレータ、トランジスタで毎回バラバラにやっている熱設計の確認を、共通UIで短時間に終わらせる

**対象デバイス：**
- 抵抗器
- 線形レギュレータ / DC-DC の放熱評価
- トランジスタ / FET / 三端子Tr

**入力項目：**

| 区分 | 項目 | 内容 |
|---|---|---|
| デバイス | `device_type` | `resistor` `regulator` `transistor` |
| デバイス | `package_type` | 例: `1608`, `TO-220`, `DPAK`, `SOT-223` |
| 発熱 | `power_loss_w` | 平均損失 |
| 発熱 | `power_profile` | `steady` `pulse` `duty` |
| 環境 | `ambient_temp_c` | 周囲温度 |
| 定格 | `max_junction_temp_c` `max_case_temp_c` | 許容温度 |
| 熱経路 | `thermal_segments[]` | 各段の名称と熱抵抗値 |
| 熱経路 | `segment_type` | `junction-case` `case-tim` `tim-sink` `sink-ambient` `body-pad` `pad-ambient` |
| 実装条件 | `copper_area` `board_layers` | 基板放熱条件 |
| 放熱部材 | `heatsink_type` `interface_material` | ヒートシンク、絶縁シート、グリス |
| 比較条件 | `candidate_parts[]` | 複数部品比較時の候補 |

**内部モデル：**
- デバイスごとに `熱抵抗セグメント列` を持つ
- 1 セグメントは `name`, `rth_c_per_w`, `delta_t_c`, `cumulative_temp_c` を持つ
- 定常時は `delta_t = power_loss_w * rth_c_per_w` で各段を積み上げる
- パルス時は初版では `参考表示` とし、将来拡張として `Zth(t)` または `RC ラダー` を受けられる形にする
- 抵抗器は `body -> terminal -> pad -> ambient`、Reg/Tr は `junction -> case/tab -> TIM -> sink/board -> ambient` を基本テンプレートとする

**判定ルール：**
1. 通常条件の `Tj` が `max_junction_temp_c` を超える場合は `不成立`
2. ワースト倍率やディレーティング条件で超える場合は `要注意` とし、通常条件OKを `不成立` にしない
3. `10℃未満` の温度マージンしか残らない場合は `要注意`
4. 最大寄与の熱抵抗セグメントを `支配段` として返す
5. ヒートシンク未指定で `sink-ambient` セグメントが必要な場合は `判定保留`
6. 候補比較時は `温度余裕`, `部品点数`, `放熱部材有無` で並べ替える

**出力：**
- 総合判定: `成立` `要注意` `不成立` `判定保留`
- `node_temps`: 各節点温度
- `segment_deltas`: 各熱抵抗での温度上昇
- `dominant_segments`: 支配的な熱抵抗段
- `required_rth_reduction`: 必要な熱抵抗削減量
- `candidate_comparison`: 候補部品/放熱案の比較
- `thermal_stack_graph`: 段積みグラフ描画用データ

**暫定API案：**

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/calc/thermal-chain/evaluate` | 熱抵抗チェーン評価を実行 |
| POST | `/calc/thermal-chain/templates` | 抵抗 / Reg / Tr のテンプレートを返す |

**暫定レスポンス例：**
```json
{
  "status": "warn",
  "ambient_temp_c": 55,
  "node_temps": [
    { "name": "ambient", "temp_c": 55.0 },
    { "name": "sink", "temp_c": 66.2 },
    { "name": "case", "temp_c": 78.4 },
    { "name": "junction", "temp_c": 109.6 }
  ],
  "segment_deltas": [
    { "name": "sink-ambient", "rth_c_per_w": 5.6, "delta_t_c": 11.2 },
    { "name": "case-sink", "rth_c_per_w": 6.1, "delta_t_c": 12.2 },
    { "name": "junction-case", "rth_c_per_w": 15.6, "delta_t_c": 31.2 }
  ],
  "dominant_segments": ["junction-case"],
  "required_rth_reduction": 8.0
}
```

**UI方針：**
- 入口で `抵抗` `Reg` `Tr` を切り替える
- 上段に `総合判定` `最大温度` `次に削るべき熱抵抗段` を固定表示する
- 中央に `P発熱源 -> Rthチェーン -> Ta周囲温度` の向きで `熱抵抗チェーンの段積みグラフ` を置き、各段の寄与がどこで効いているかを見せる
- 下段に `候補比較` `必要な放熱改善量` `支配段` を並べる
- `Tj だけ` ではなく `途中の各節点温度` を出し、構造関数風の読み方ができるようにする

### ⑮ 全体詳細設計【モジュール分割と責務境界】

BitsKeep 全体は、`在庫・案件の業務基盤` と `設計判断支援` を一つの画面群に見せるが、内部実装は責務ごとに分割する。特に、`高頻度・小修正系` と `高損害診断系` を同じ種類のツールとして扱わない。

**全体モジュール構成：**

| モジュール | 主責務 | バックエンド実装単位 | フロント実装単位 | 主データ |
|---|---|---|---|---|
| Core Inventory | 部品、在庫、棚、商社、入出庫、警告 | Laravel Model / Service / Query | 一覧、詳細、登録、棚画面 | `components`, `inventory_blocks`, `transactions`, `locations`, `suppliers` |
| Project Master | 統合案件マスタ、案件選択、案件部品紐づけ | ProjectService, SyncService | 案件管理画面、共通 `ProjectComboBox` | `projects`, `component_project` |
| Search & Compare | グローバル検索、類似部品、比較 | SearchQueryService, CompareService | ホーム検索ランチャー、比較画面 | 検索インデックス相当の集約結果 |
| Tool Hub | 設計解析ツール導線、最近使ったツール、クイック起動 | ToolCatalogService | `design_tools.html` 相当のハブ、ホームのカード | ツール定義、最近使った機能 |
| Calc Foundation | 入出力正規化、共通バリデーション、仮定条件表示、グラフ用レスポンス整形 | `CalcInputNormalizer`, `CalcResponseBuilder` | ツール共通フォーム、結果サマリー、グラフ描画部品 | 解析入力、解析結果 |
| Search/Optimize Engines | 合成抵抗/容量探索、E系列近似、候補比較 | Solver / Search Engine | 条件入力、候補一覧、比較表 | E系列、在庫候補、探索結果 |
| Rule/Graph Diagnostics | 起動依存、保護協調、注入電流経路、熱抵抗チェーン | RuleEngine / GraphEvaluator | 依存グラフ、タイムライン、段積みグラフ | ノード、ルール、テンプレート |
| Reference Catalog | ロジックIC、コネクタ設計/ピン配置、DIP/ジャンパ逆引き | CatalogService / Static Catalog Loader | 検索即応UI、視点切替UI、ピンマップUI | 構造化カタログ |
| External Sync & Audit | Notion 同期、監査ログ、同期履歴 | SyncJob, AuditService | 同期ボタン、同期結果表示、監査ログ画面 | `audit_logs`, 同期履歴 |
| User Preference | クイックアクション順、最近使った機能、既定の事業/案件 | PreferenceService | ホーム並び替え、既定値反映 | `user_preferences` または `users.settings_json` |

**実装境界の基本方針：**
- 受動部品ネットワーク/分圧設計、通常分圧、VR分圧、保存済み解析はサーバ側計算を利用する。設計解析ツールハブでは `ネットワーク探索` / `分圧` / `可変抵抗` をメインタブとして扱い、別ページ誘導ではなく同じ操作面を埋め込む実装とする
- 設計解析ツールハブ初版の ADC、寿命、誤差、NTC/PTC温度変換、電流検出、IF、電源、比較器、周波数応答、熱、保護、起動診断、ロジックIC参照、コネクタ/ケーブル/ジャンパはフロント計算を正本とし、共通の `verdict` `summary` `assumptions` `warnings` `next_actions` で表示する
- 設計解析ツールハブ内の温度系は `NTC/PTC温度変換` であり、通常分圧/VR分圧の候補選定は持たない
- 将来、解析条件の監査性や複数ユーザー共有が必要になったツールから個別API化する
- `高頻度・小修正系` は 5 秒以内に使える軽量UIを優先し、`高損害診断系` は入力負荷が増えても原因追跡力を優先する

|---|---|---|

| `user_auth_providers` | SNSログイン連携先、プロバイダユーザーID、連携状態 | SNSログイン導入時に追加する |
| `project_sync_runs` | Notion同期の実行履歴、件数、失敗理由 | 初版から導入する |
| `calc_runs` | 解析入力/結果の再参照、共有、監査 | 初版は任意。必要最小限なら保存なしでも可 |
| `calc_presets` | よく使う条件セット、テンプレート保存 | 初版は見送り可 |
| `reference_catalog_meta` | カタログの版管理、更新日 | 初版は静的JSON管理でも可 |

### ⑯ 実現可否整理【実装対象と実現困難の切り分け】

**判定記号：**
- `◎`: 初版スコープでそのまま実装可
- `○`: スコープを限定すれば実装可
- `△`: 追加調査またはデータ整備後に実装可
- `×`: 現時点では見送り

**運用ルール：**
- `◎` と `○` は実装対象として扱い、`制作管理/実装進捗チェックリスト.md` に落とし込む
- `△` と `×` は現時点では実現困難として扱い、仕様書に記録のみ残す
- `△` は将来否定ではなく、入力元・部品モデル・辞書整備が揃うまで保留するものを指す

| アナログスイッチ / 多重化前段成立性 | △ | 実装可だが対象回路のテンプレート化が前提 | ADC前段、センサ切替など頻出形に限定する |
| FPGAピン / バンク整合、RTL/ファーム/レジスタ整合 | × | 現状の BitsKeep には設計データ入力元がない | 将来、設計ファイル取込基盤を作るまで見送る |
| ノイズ侵入経路 / リターンパス / EMIホットスポット | × | 基板レイアウトや配線情報なしでは判断精度が出ない | 現時点では記録のみ |

### ⑰ 初版の実装順序と採用境界

**実装波次：**
1. 運用基盤を先に固める
   - ホーム、横断検索、案件コンボボックス、案件管理、監査ログ
   - この段階で `案件選択の迷い` と `部品運用` を止めないことを優先する
2. 計算系の初版本隊を入れる
   - エンジニア電卓
   - 抵抗/容量ネットワーク探索
   - ADC、誤差/歩留まり、電流検出、インタフェース余裕、電源余裕
3. 高頻度・小修正系を先に一部入れる
   - コネクタ設計/ピン配置
   - ケーブル/ジャンパ/0Ω系の軽量参照ツール
4. 高損害診断系の初版を限定投入する
   - 起動依存診断
   - 熱抵抗チェーン可視化
5. 入力保護/保護協調や観測性診断は、テンプレートとデータ整備の目処が立ってから投入する

**チェックリスト反映ルール：**
- 上記 1〜4 に入る機能だけを実装進捗チェックリストへ載せる
- 5 の群、および `⑯-2. 現時点では実現困難` に入る機能は、仕様書に残してもチェックリストには載せない

**採用してよい機能の条件：**
- 入力項目が整理でき、代表テンプレートで再現性のあるテストケースを作れる
- 出力が `次に何を直すか` `どの候補を選ぶか` に繋がる
- 仮定条件を明示できる
- 結果を `summary + warnings + chart_model + next_actions` に正規化できる

**まだ採用しない方がよい機能の条件：**
- 一般化しすぎると入力負荷だけ増え、初版の精度が下がる
- 設計ファイル、基板レイアウト、未整備の部品辞書など、まだ存在しない入力元に依存する
- 物理シミュレータ級の汎用性を目指さないと成立しない
- `面白い` が `毎月使う` に繋がらない

## 21. 使い方ガイド画像化要件（2026-05-13）

- アプリ内ヘルプ `/help` は、文章だけではなく、Headless Chrome で取得した実画面スナップショットを併用する。
- ガイド画像は、機能全体を把握する全体画像と、検索欄、詳細条件、スペック入力、データシート解析補助、入庫モーダルなどの操作箇所を確認する部分拡大画像を組み合わせる。
- 対象画面はダッシュボード、部品一覧、部品詳細、部品登録、部品比較、マスタ管理、設計ツール、データのバックアップを最低範囲とする。
- ガイド画像の保存先は `resources/help/screenshots/` とし、認証付きルート `/help-guide/screenshots/{filename}` から配信する。`public/help/` や `public/help-guide/` は Laravel の `/help` ルートとの衝突や未認証直配信のリスクがあるため使わない。
- ガイド用スクリーンショットにはログイン表示名やメールアドレスなど、説明に不要な個人情報を写さない。撮影スクリプト側でヘッダのログイン表示とメールアドレスをマスクしてから保存する。
- 撮影スクリプト `npm run capture:guide` は `BITSKEEP_URL`、`BITSKEEP_GUIDE_EMAIL`、`BITSKEEP_GUIDE_PASSWORD` を必須とし、認証情報をソースに直書きしない。共有環境の実データを撮影する場合は `BITSKEEP_GUIDE_ALLOW_REAL_DATA=1` を明示し、公開ガイドに掲載してよいデータだけを使う。
- README は画像を重複掲載せず、ログイン後ヘッダの「使い方」および `/help` の画像付きガイドへ誘導する。
